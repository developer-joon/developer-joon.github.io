AWS는 2026년 11월 23일 Amazon SSM Agent의 CVE-2026-134069를 공개했다. 특정 조건에서 2026년 9월 9일 이전에 출시된 같은 AWS 제공 Windows Server AMI로 만든 인스턴스들이 동일한 SSM Agent 등록 키를 공유할 수 있는 문제다.[1] 영향받는 Agent 버전은 3.3.5226.0 미만이지만, 기존 인스턴스에서 Agent만 3.3.5226.0 이상으로 인플레이스 업그레이드해도 이미 생성된 공유 키는 남는다.[1]

영향을 이용하려면 Default Host Management Configuration(DHMC)으로 관리되는 인스턴스에 로컬 비관리자 접근이 필요하다. AWS 설명에 따르면 이 사용자는 DHMC 역할 자격 증명을 얻을 수 있고, 기본적으로 그 자격 증명은 제한된 Systems Manager 작업만 허용한다.[1] 전제조건과 기본 권한 범위를 빼고 “모든 SSM 인스턴스가 원격 장악된다”고 확대하면 안 된다. 반대로 로컬 접근이 가능한 다중 사용자 서버에서는 단순 Agent 업데이트로 티켓을 닫아서도 안 된다.

## 바이너리 버전과 이미지에서 생성된 상태는 다른 자산이다

패키지 업데이트는 실행 파일을 교체한다. 그러나 등록 키처럼 첫 부팅이나 이미지 준비 과정에서 만들어져 로컬 상태로 보존되는 값은 새 바이너리를 설치해도 자동으로 다시 생성되지 않을 수 있다. AWS 권고가 “업데이트”가 아니라 수정된 AMI로 인스턴스를 **교체**하라는 이유다.[1]

릴리스 3.3.5226.0에는 `RegistrationInfo` 로딩 로직 업데이트가 포함돼 있으며, 2026년 8월 20일 공개됐다.[2] 하지만 릴리스 노트에 해당 코드 변경이 있다는 사실과 기존 인스턴스의 등록 상태가 교체됐다는 사실은 별개다. 보안 판정에는 세 축이 필요하다.

| 판정 축 | 질문 | 증거 |
|---|---|---|
| 이미지 기원 | 어떤 AWS Windows Server AMI에서 시작했는가 | AMI ID, 소유자, 이름, 출시일, 시작 시각 |
| 실행 코드 | 현재 어떤 SSM Agent가 동작하는가 | Agent 버전, 서비스 시작 시각, 배포 기록 |
| 등록 상태 | 취약 AMI에서 생성된 상태가 계속 남았는가 | 교체 여부, 새 인스턴스 ID, 관리 등록 이력 |

세 축 중 Agent 버전만 최신이라고 해서 안전 판정이 되지 않는다. AWS는 영향 AMI에서 시작한 인스턴스가 인플레이스 업그레이드 뒤에도 영향을 받는다고 명시했다.[1]

## 자산 인벤토리는 AMI 계보와 DHMC를 함께 본다

먼저 모든 Windows EC2 인스턴스의 인스턴스 ID, 계정·리전, AMI ID, 시작 시각, SSM 관리 상태, Agent 버전, DHMC 적용 여부를 수집한다. AMI ID만으로 끝내지 않고 AMI 소유자가 AWS인지, 출시일이 2026년 9월 9일 이전인지 확인한다. 사내 골든 AMI는 그 자체의 생성일보다 부모 AMI 계보가 중요하다. 오래된 AWS AMI를 기반으로 10월에 다시 만든 사내 이미지라면 날짜만 보고 제외할 수 없다.

Auto Scaling 시작 템플릿, EC2 Image Builder 파이프라인, 백업 복원 정의, 재해복구 문서도 함께 찾는다. 현재 실행 중인 인스턴스를 모두 바꿔도 시작 템플릿이 취약 이미지를 가리키면 다음 스케일아웃이나 장애 복구에서 문제가 되살아난다.

우선순위는 다음 조건으로 높인다.

- 2026년 9월 9일 이전 AWS Windows Server AMI 또는 그 파생 이미지
- DHMC를 통해 관리되는 인스턴스
- 로컬 비관리자 로그인이 허용되는 점프 서버, 개발·교육 서버, 다중 사용자 호스트
- 광범위한 DHMC 역할 정책이나 여러 계정·리전에 걸친 역할 신뢰
- 이미지 계보 또는 로컬 접근 주체를 확인할 수 없는 자산

DHMC 미사용이나 로컬 비관리자 접근 부재는 중요한 완화 조건이지만, 추정으로 채우지 않는다. Systems Manager 설정과 IAM 역할, 로컬 그룹 정책, 원격 데스크톱 권한, 애플리케이션이 만드는 로컬 계정을 각각 확인한다.

## 인플레이스 업그레이드와 Vault 삭제를 복구로 오인하지 않는다

AWS는 영향 AMI에서 시작한 기존 인스턴스의 키가 Agent 인플레이스 업그레이드 후에도 남는다고 설명한다. 또한 Agent의 Vault를 삭제하는 것은 지원되는 완화책이 아니며 DHMC 관리 인스턴스를 손상시킨다고 경고한다.[1] 따라서 키 파일 위치를 찾아 지우거나 재사용 가능성을 시험하는 방식은 방어 검증이 아니다.

즉시 교체가 어렵다면 AWS가 제시한 임시 완화 방향에 따라 영향 후보 인스턴스의 로컬 비관리자 접근을 제한한다.[1] 운영 중인 서비스 계정과 관리 도구가 로컬 로그온 권한을 사용하는지 먼저 확인해 가용성 사고를 피한다. 동시에 DHMC 역할 정책을 최소 권한으로 줄이고, CloudTrail과 Systems Manager 활동에서 평소와 다른 관리 호출을 검토한다. 이는 교체까지의 위험 축소이지 최종 해결이 아니다.

Agent를 3.3.5226.0 이상으로 올리는 작업 자체도 필요할 수 있다. 새 AMI와 새 인스턴스가 수정된 Agent를 포함하는지 확인해야 하기 때문이다. 다만 변경 티켓에서 “Agent 업데이트 완료”와 “영향 인스턴스 교체 완료”를 별도 상태로 둔다.

## 수정 AMI로 교체하는 안전한 순서

교체는 기존 서버를 종료하고 새 서버를 켜는 단순 작업이 아니다. 구성과 데이터, 네트워크 신원, SSM 등록, IAM 정책을 새 인스턴스로 옮기면서 취약 상태를 복제하지 않아야 한다.

1. **수정 기반 선택:** 2026년 9월 9일 이후 AWS 제공 Windows Server AMI인지, Agent 3.3.5226.0 이상인지 확인한다.[1]
2. **골든 이미지 재생성:** 기존 AMI를 그대로 복제하지 말고 수정 기반에서 빌드 파이프라인을 다시 실행한다. 설치 산출물과 구성은 검토된 소스에서 적용한다.
3. **격리 배포:** 운영 트래픽과 분리된 서브넷 또는 대상 그룹에 새 인스턴스를 올리고 최소 IAM 역할을 부여한다.
4. **관리 기능 검증:** 새 인스턴스가 Systems Manager에 고유한 관리 노드로 나타나고, 승인된 세션·명령·패치 작업만 수행되는지 확인한다.
5. **업무 회귀 검증:** 서비스 시작, 모니터링, 백업, 인증서, 시간 동기화, 로그 전송을 점검한다.
6. **단계적 전환:** 소수 인스턴스로 카나리 전환한 뒤 오류율과 SSM 연결 상태를 관찰하고 나머지를 교체한다.
7. **이전 자산 폐기:** 트래픽과 관리 작업이 새 인스턴스로 이동했음을 확인한 뒤 이전 인스턴스를 격리·종료하고 보존 정책에 맞게 폐기한다.

새 인스턴스에 기존 시스템 볼륨 전체나 Agent 상태 디렉터리를 복제하면 문제 상태도 함께 옮길 수 있다. 애플리케이션 데이터와 운영체제·Agent 상태를 구분하고, 필요한 데이터만 지원되는 방식으로 이전한다.

## 교체 후에는 등록·정책·로그를 함께 검증한다

성공 기준은 새 서버가 “Online”으로 보이는 것만이 아니다. 인스턴스 ID, 관리 노드 식별, AMI ID와 Agent 버전이 기대한 값인지 확인한다. DHMC 역할이 의도한 계정·리전과 태그 조건에만 적용되고, 세션 관리자와 Run Command 같은 기능의 권한이 업무 요구보다 넓지 않은지도 점검한다.

회귀 검증표에는 다음을 넣는다.

- 새 인스턴스가 수정된 AMI 계보와 3.3.5226.0 이상 Agent를 사용한다.
- 기존 인스턴스와 다른 인스턴스·관리 노드 식별자로 등록됐다.
- 태그 기반 대상 지정이 예상 인스턴스만 포함한다.
- 승인된 운영 역할은 필요한 SSM 작업을 수행하고 일반 사용자는 수행하지 못한다.
- CloudTrail, SSM 세션·명령 로그, Windows 이벤트가 중앙 저장소로 전달된다.
- 시작 템플릿과 이미지 파이프라인이 새 AMI를 고정적으로 참조한다.
- 롤백 절차가 취약한 이전 AMI를 재기동하는 방식이 아니다.

권한 검증은 실제 자격 증명을 추출하거나 재사용하지 않는다. 승인된 IAM 주체의 정상 요청과 명시적 거부 결과를 확인한다. 로컬 비관리자 계정으로 등록 키 위치를 탐색하는 재현은 필요하지 않다.

## 이상 징후가 있다면 자격 증명과 행위를 별도로 조사한다

공개 권고가 특정 조직의 악용을 의미하지는 않는다. 그러나 영향 조건에 해당하고 로컬 비관리자 접근자가 있었다면 노출 기간의 CloudTrail, Systems Manager API, 세션·명령 이력을 검토한다. 평소와 다른 관리 노드 등록, 예상하지 못한 명령·세션, 역할 자격 증명 사용, 정책 변경을 시간순으로 연결한다.

이상 징후가 발견되면 인스턴스를 격리하고 로그와 디스크 증거를 보존한다. DHMC 역할 세션과 관련 정책을 검토하고, 필요한 경우 역할 신뢰·권한을 수정하며 노출 가능성이 있는 자격 증명을 폐기한다. 단순히 인스턴스를 종료하면 휘발성 증거와 중앙 전송 전 로그가 사라질 수 있으므로 조직의 사고 대응 절차를 따른다.

아무 징후가 없더라도 로그 보존이 영향 기간을 덮지 못하면 “침해 없음”으로 닫지 않는다. 확인 가능한 기간과 공백, 접근 가능했던 로컬 사용자, 역할 정책의 실제 범위를 함께 기록한다. 교체는 취약 상태 제거이고, 과거 악용 여부 판정은 별도의 증거 문제다.

## 종료 기준은 현재와 미래의 재발 경로를 모두 없앤다

완료 판정은 실행 인스턴스만 세지 않는다. 이미지 파이프라인, 시작 템플릿, 복구 자동화까지 수정되어야 한다.

- 영향 후보를 계정·리전·AMI 계보·DHMC·로컬 접근 기준으로 분류했다.
- 모든 영향 인스턴스가 수정 AMI에서 시작한 새 인스턴스로 교체됐다.
- 새 인스턴스의 Agent, 고유 등록, IAM 최소 권한과 로그 전달을 확인했다.
- 취약 AMI를 참조하던 골든 이미지, 템플릿, Auto Scaling, DR 정의를 갱신했다.
- 이전 인스턴스와 이미지의 재사용을 차단하고 예외의 소유자·기한을 정했다.
- 노출 기간의 SSM·CloudTrail 활동을 검토하고 공백과 잔여 위험을 기록했다.

이번 사례가 보여 주는 핵심은 패키지 버전이 시스템의 보안 상태 전체를 대표하지 않는다는 점이다. 이미지 생성 시 만들어진 상태는 새 이미지에서 다시 시작해야 치유될 수 있다. 불변 인프라는 단순한 배포 취향이 아니라, 출처를 설명할 수 없는 상태를 버리고 검증된 기원으로 돌아가는 복구 수단이다.
