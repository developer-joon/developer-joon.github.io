Metabase CVE-2026-72898은 “패치만 하면 끝”이라고 보기 어려운 취약점이다. 인증하지 않은 원격 공격자가 Metabase application database에 임의 SQL을 주입해 관리자 권한을 얻을 수 있고, Metabase는 실제 악용을 확인했다.[1][2]

싱가포르 CSA는 2026년 11월 4일 CVSS 3.1 10.0, 공개 PoC, active exploitation을 알리며 즉시 업데이트를 권고했다.[1] Metabase Cloud는 벤더가 이미 패치했다고 밝혔지만, 자체 호스팅 인스턴스는 운영자가 영향 범위와 사후조치를 직접 확인해야 한다.[3]

## 수정 버전은 major line별로 다르다

| Release line | 최초 수정 버전 |
|---|---:|
| 0.58 / 1.58 | 0.58.24 / 1.58.24 |
| 0.59 / 1.59 | 0.59.21 / 1.59.21 |
| 0.60 / 1.60 | 0.60.17 / 1.60.17 |
| 0.61 / 1.61 | 0.61.11 / 1.61.11 |
| 0.62 / 1.62 | 0.62.9 / 1.62.9 |
| 0.63 / 1.63 | 0.63.5 / 1.63.5 |

이 표는 CSA와 Metabase advisory의 수정 release를 정리한 것이다.[1][2] `latest` tag만 다시 pull하지 말고 실행 중 image digest와 application의 실제 버전을 함께 남긴다. Rolling update가 끝나기 전 오래된 pod가 남아 있으면 외부 traffic을 받을 수 있다.

## 임시 차단은 패치가 아니다

즉시 업그레이드할 수 없다면 `/api/session/reset_password` endpoint를 차단하는 것이 공식 임시 workaround다.[1][2] 다만 이는 취약 artifact를 고치지 않는다.

상태를 다음처럼 나눈다.

```text
artifact_state: affected | patched | unknown
endpoint_state: public | blocked_temporarily | private | unknown
incident_state: no_indicators_observed | suspicious | confirmed | evidence_missing
credential_state: unchanged | rotation_in_progress | rotated
```

이 이름은 Metabase API field가 아니라 이 글의 운영 제안이다. `blocked_temporarily`를 `patched`로 승격하지 않는다.

## 패치 뒤 세션과 비밀을 회전하는 이유

Metabase는 공격자가 관리자 권한을 얻은 뒤 설정을 바꾸고, 연결 DB의 저장 자격 증명을 훔치며, 해당 연결이 읽을 수 있는 데이터를 조회·내보낼 수 있다고 설명한다.[2][3] 그래서 공개 endpoint가 노출됐던 인스턴스에는 다음 사후조치가 필요하다.

1. active user session을 폐기한다.
2. 알 수 없는 API key를 삭제한다.
3. 관리자 계정의 예상하지 못한 변경을 검토한다.
4. 연결된 database 자격 증명을 회전한다.
5. warehouse log와 Metabase activity/query history를 조사한다.[1][3]

패치 전 탈취된 세션이나 DB 비밀은 새 binary를 배포해도 자동 폐기되지 않는다. 회전 범위는 Metabase application DB 계정만이 아니라, Metabase가 저장한 각 warehouse credential과 외부 SSO·API 통합까지 실제 구성에 맞춰 결정한다.

## 안전한 확인 절차

공격을 재현하지 않고도 필요한 운영 증거를 모을 수 있다.

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${METABASE_URL:?set the reviewed base URL}"
curl --fail --silent --show-error \
  "$METABASE_URL/api/session/properties" \
  | python -m json.tool >/dev/null
```

이 예시는 endpoint 응답 형식과 배포마다 공개 범위가 달라질 수 있는 **제안된 probe**이며 이 글에서 실행하지 않았다. 인증 토큰이나 application DB 내용을 로그에 출력하지 말고, 버전은 관리자 화면의 About 정보와 배포 manifest를 교차 확인하는 편이 안전하다.

공식 incident 글은 관찰된 요청 흐름으로 `POST /api/session/reset_password`의 400 뒤 `GET /api/user/current` 200을 제시한다.[3] 이는 중요한 탐지 단서지만, 그 패턴이 없다는 것만으로 침해가 없었다고 증명할 수는 없다. 로그 보존 기간, reverse proxy field, endpoint naming 차이도 함께 확인한다.

## Security Center도 coverage를 자동 보증하지 않는다

Metabase Security Center는 self-hosted Pro·Enterprise에서 advisory와 알림을 제공한다. Cloud는 자동 패치되고, air-gapped 인스턴스는 registry를 조회할 수 없어 Security Center를 받지 못한다.[4] OSS나 air-gapped 환경은 GitHub advisory와 release monitoring을 별도 운영해야 한다.

완료 조건은 `버전이 올라갔다` 한 줄이 아니다.

- 수정 release가 모든 runtime에 배포됐다.
- 임시 endpoint 차단의 유지·해제 결정이 기록됐다.
- 세션, 관리자, API key, DB credential 검토가 끝났다.
- 관련 로그의 보존 범위와 미확인 구간이 명시됐다.
- 새 credential이 실제 workload에 적용되고 옛 credential이 거부된다.

실제 악용된 인증 우회형 SQL 주입에서는 패치와 침해 대응을 같은 변경 ticket에 넣되, 각각 독립된 완료 증거를 요구해야 한다.
