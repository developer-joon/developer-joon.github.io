번역 모델을 로컬에서 실행하는 이유는 단순한 비용 절감만이 아니다. 계약서나 연구 문서처럼 외부 전송이 어려운 텍스트를 다루고, 네트워크가 끊긴 현장에서 일정한 지연시간을 얻으려면 모델이 기기 안에서 끝까지 동작해야 한다.

Preferred Networks(PFN)는 2026년 11월 5일 PLaMo 3 Translate의 가중치를 공개했다. 모델은 0.8B, 2B, 8B, 31B 네 크기이며 영어와 일본어를 포함한 53개 언어 번역과 스마트폰·노트북·사내 서버의 오프라인 실행을 내세운다.[1]

## open-weight와 오픈소스는 같은 말이 아니다

PFN이 공개한 것은 실행 가능한 모델 가중치다. 이를 OSI 승인 오픈소스 라이선스가 적용된 범용 소프트웨어와 같은 의미로 읽으면 안 된다. 모델 사용에는 PLaMo Community License 조건이 붙는다.

공식 발표는 개인과 최근 회계연도 매출 10억 엔 이하 조직이 상업·비상업 용도로 무료 이용할 수 있고, 기준을 넘는 조직은 PFN과 별도 상업 라이선스 계약이 필요하다고 설명한다.[1] 조직의 매출 기준, 계열사 합산 여부, 배포 형태처럼 실제 계약 판단에 필요한 세부사항은 원문 라이선스와 법무 검토로 확인해야 한다.

따라서 모델 도입 표에는 최소한 다음 열이 필요하다.

| 항목 | 확인할 값 |
|---|---|
| 배포물 | 정확한 repository와 revision |
| 모델 크기 | 0.8B / 2B / 8B / 31B |
| 사용 목적 | 내부 이용 / 제품 내장 / 재배포 |
| 조직 매출 | 라이선스 기준 적용 여부 |
| 데이터 경로 | 입력·출력이 외부로 나가는지 |
| 의존성 | runtime과 tokenizer의 별도 라이선스 |

“가중치를 내려받을 수 있다”는 사실만으로 재배포와 모든 상업 이용이 무조건 허용되는 것은 아니다.

## 0.8B 모델이 흥미로운 이유

가장 작은 0.8B 모델은 스마트폰 비행기 모드에서 실시간 번역하는 데모가 공개됐다.[1] 작은 모델은 메모리와 전력, 시작 시간에서 유리하지만 문맥 유지와 희귀어, 형식 보존에서는 큰 모델보다 불리할 수 있다.

그래서 “기기에서 실행됐다”와 “업무 문서를 안전하게 번역했다”를 분리해 평가해야 한다. 실무 품질은 BLEU 같은 평균 점수 하나보다 다음 오류에서 드러난다.

- 숫자, 통화, 날짜, 단위가 바뀌는가
- 사람·회사·제품 고유명사를 임의로 번역하는가
- 표의 행과 열, Markdown 링크, placeholder를 보존하는가
- 긴 문서에서 앞서 정의한 용어를 일관되게 쓰는가
- 한국어가 포함된 다국어 문장에서 언어를 혼합하지 않는가
- 번역할 수 없는 구간을 누락하거나 만들어내지 않는가

PFN의 품질 비교는 자체 평가와 proprietary benchmark를 포함한다.[1] 공급자 그래프는 후보 선정 자료로는 유용하지만 독립 재현 결과는 아니다.

## 오프라인 검증은 network 차단부터 시작한다

아래는 **아직 실행하지 않은 검증 fixture 제안**이다. 같은 입력 corpus를 네 모델과 비교 대상 번역 API에 넣되, 로컬 모델은 network namespace 또는 방화벽으로 외부 연결을 차단한다.

```text
Corpus A: 한국어↔영어 일반 문장 100개
Corpus B: 숫자·단위·고유명사 중심 문장 100개
Corpus C: Markdown·표·placeholder가 있는 문서 30개
Corpus D: 한국어를 포함한 다국어 문장 50개
```

각 모델에서 다음을 기록한다.

```text
model_revision
runtime_version
quantization
cold_start_ms
first_token_ms
chars_per_second
peak_rss_mb
input_hash
output_hash
format_preservation_failures
critical_entity_errors
```

Cloud API 비교에서는 품질과 지연 외에 `data_left_device=true`를 별도 열로 둔다. 로컬 모델이 외부 전송을 하지 않는 장점과 클라우드 모델의 품질을 하나의 총점으로 숨기면 개인정보 경계가 보이지 않는다.

## 완전 오프라인이라는 주장도 범위를 고정해야 한다

PFN은 사용자 관리 기기나 서버에서 실행하면 원문과 번역 결과가 외부 cloud server로 전송되지 않는다고 설명한다.[1] 이는 모델 실행 경로에 대한 설명이지, 사용한 애플리케이션 전체가 자동으로 오프라인이라는 보장은 아니다.

실제 제품은 다음 경로를 확인해야 한다.

- 모델 다운로드와 update checker
- crash report와 analytics SDK
- remote font, spell checker, telemetry
- 번역 기록 동기화
- 사전·용어집 조회

모델 프로세스만 network를 쓰지 않아도 shell 애플리케이션이 원문을 analytics event에 넣으면 데이터 경계는 깨진다. Packet capture와 DNS log로 전체 process tree를 확인해야 한다.

## 모델 크기는 품질 순서가 아니라 운영 선택지다

31B가 항상 정답은 아니다. 더 큰 모델은 품질 여지가 있지만 GPU 메모리, 시작 시간, 전력, 배포 크기가 늘어난다. 0.8B는 제한된 기기에서 충분히 빠를 수 있지만 중요 문서의 숫자 오류 비용이 더 클 수 있다.

다음과 같이 workload별 허용선을 먼저 정하는 편이 낫다.

| 용도 | 우선 지표 | 실패 시 fallback |
|---|---|---|
| 여행용 짧은 문장 | 지연, 배터리 | 원문 병기 |
| 사내 검색용 초벌 | 처리량, 외부 전송 금지 | 사람이 최종 검토 |
| 계약서 번역 | 숫자·용어 정확성 | 전문 번역가 검토 |
| 재난 현장 | 오프라인 가용성 | 필수 문구 사전 탑재 |

문장 평균 점수가 좋아도 계약 금액 하나를 바꾸면 배포할 수 없다. 반대로 모든 문장을 출판 품질로 만들 필요가 없는 초벌 검색에서는 작은 모델의 privacy와 처리량이 더 중요할 수 있다.

## 도입 결론

PLaMo 3 Translate의 핵심은 하나의 “최고 모델”이 아니라, 0.8B부터 31B까지 같은 번역 목적을 서로 다른 기기 경계에 배치할 수 있다는 점이다. 다만 open-weight를 무제한 오픈소스로 부르지 말고, PFN 자체 품질 수치를 독립 성능처럼 쓰지 않아야 한다.

검증 순서는 간단하다. 정확한 revision과 라이선스를 고정하고, network를 차단한 뒤, 한국어가 포함된 실제 문서 corpus에서 지연·메모리·형식·숫자·고유명사를 함께 측정한다. 결과가 허용선을 넘지 못하면 더 큰 모델이나 사람 검토로 fallback한다. 오프라인 번역의 성공 조건은 “문장이 나왔다”가 아니라 **데이터가 나가지 않았고, 중요한 내용이 바뀌지 않았으며, 조직이 그 모델을 사용할 권리가 있음**을 함께 증명하는 것이다.
