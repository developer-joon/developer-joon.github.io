2026년 11월 25일 Vates는 Xen Orchestra의 CVE-2026-133469가 실제 공격에 이용되고 있다고 공지를 갱신했다. CISA도 같은 날 이 취약점을 Known Exploited Vulnerabilities(KEV) 카탈로그에 추가했다.[1][2] 이는 단순히 “패치를 서두르라”는 알림이 아니다. Xen Orchestra는 여러 XCP-ng 호스트와 가상 머신, 백업 저장소를 제어하는 관리면이다. 이 경계가 무너지면 조사 범위도 웹 애플리케이션 한 대에서 끝나지 않는다.

공급자가 제시한 수정 버전은 Xen Orchestra 6.9.2(Stable)와 6.10.1(Latest), 패키지 기준으로는 `xo-server` 5.211.2와 5.213.1이다.[1] 그러나 수정 버전을 설치했다는 사실은 이후 악용을 막는 통제일 뿐, 패치 전에 침해되지 않았다는 증명은 아니다. 대응은 **노출 차단, 증거 보존, 패치, 침해 선별, 자격 증명 회전, 신뢰할 수 있는 복구**를 하나의 변경 계획으로 묶어야 한다.

## 관리 애플리케이션이 아니라 제어면 사고로 분류한다

Vates 공지에 따르면 인증 우회에 성공한 공격자는 관리자 권한으로 동작할 수 있고, 관리되는 풀에서 코드 실행이나 XCP-ng 노드의 `root` 권한 장악으로 영향이 확장될 수 있다.[1] GitHub 보안 권고도 이 취약점을 Critical, CVSS 3.1 9.8로 평가한다.[3] 여기서 중요한 것은 점수보다 권한의 전파 방향이다.

일반 웹 서비스라면 애플리케이션 계정과 데이터베이스를 중심으로 사고 범위를 정할 수 있다. Xen Orchestra에는 호스트 제어 권한, 풀 시크릿, 백업 원격지, 프록시, 메일 서버와 OTP 설정처럼 다른 시스템으로 이어지는 연결 정보가 모인다. 따라서 사고 티켓의 자산 범위에는 최소한 다음이 포함돼야 한다.

| 조사 영역 | 확인할 대상 | 보존할 증거 |
|---|---|---|
| Xen Orchestra | 배포 채널, 실제 실행 버전, 관리자·토큰 변경 | VM 스냅샷이 아닌 별도 로그 사본, 설정 내보내기, 변경 시각 |
| XCP-ng 풀 | 호스트·풀 구성, 비정상 VM과 작업 | 호스트 로그, 작업 이력, VM 생성·시작 기록 |
| 관리 네트워크 | 외부 노출, 프록시·WAF·방화벽 경로 | 흐름 로그, 프록시 접근 로그, 정책 변경 이력 |
| 백업·스토리지 | NFS·S3·Azure·SMB 연결과 권한 | 접근 로그, 객체 변경·삭제 기록, 자격 증명 사용 이력 |
| 외부 연동 | SMTP, 디렉터리, SSO, 알림 채널 | 인증 로그, 토큰 발급·회수 기록, 관리자 변경 |

이 표는 Vates 제품의 공식 데이터 모델이 아니라 조직이 사고 대응을 위해 만드는 조사 범위다. 특히 백업은 “복구 수단이 있으니 안전하다”가 아니라, 관리면이 가진 쓰기·삭제 권한 때문에 별도의 잠재 피해 자산으로 취급해야 한다.

## 첫 조치는 패치 버튼보다 노출 경로 통제다

공급자는 Xen Orchestra를 인터넷에 노출하지 말고 전용 관리 네트워크에 두라고 권고한다.[1] 우선 방화벽, 로드 밸런서, 리버스 프록시, VPN, 포트 포워딩, 임시 터널을 모두 확인한다. DNS 레코드가 없다는 이유만으로 비노출로 판정하지 않는다. 공인 IP에 직접 연결된 경로와 클라우드 보안 그룹도 별도로 본다.

긴급 차단은 운영자 접근을 완전히 끊는 방식이 아니라, 승인된 관리 VPN 또는 점프 호스트에서만 도달하도록 좁히는 방식이 바람직하다. 변경 전후에는 정상 관리자 로그인, 풀 조회, 백업 작업의 상태를 확인하되 새 백업이나 대규모 작업을 시작해 증거를 덮어쓰지 않는다. 공급자가 공개한 특정 인프라 차단과 WAF 패턴은 알려진 캠페인의 일부만 막는다. 공지 자체도 정규식 기반 차단이 다른 형식에 우회될 수 있다고 경고하므로 임시 완화책을 패치 대체재로 기록하면 안 된다.[1]

보존 순서도 중요하다. 시스템을 종료하거나 재설치하기 전에 시간 동기화 상태, 현재 연결, 실행 프로세스, 최근 계정·토큰·VM·작업 변경, 프록시와 네트워크 흐름 로그를 승인된 절차로 복제한다. 수집 도구를 새로 설치하거나 광범위한 스캔을 실행하면 타임스탬프와 휘발성 상태가 달라질 수 있다. 조직의 포렌식 절차와 법무·개인정보 보존 요건이 있다면 그 절차가 우선한다.

## 수정 버전은 설치 방식별로 증명한다

어플라이언스 사용자는 Stable과 Latest 채널을 구분해 각각 6.9.2, 6.10.1 이상인지 확인한다. 패키지 인벤토리에서는 `xo-server`가 Stable 5.211.2 또는 Latest 5.213.1 이상인지 대조한다. 소스 설치는 Vates가 최신 `master` 업데이트를 강하게 권고하지만, 운영팀은 단순 브랜치 이름 대신 배포한 커밋, 빌드 시각, 프로세스 재시작 시각을 변경 기록에 남겨야 한다.[1]

검증은 다음 세 층을 서로 대체하지 않게 한다.

1. **배포 증거:** 공급자 채널과 패키지 또는 커밋이 수정선을 포함한다.
2. **런타임 증거:** 현재 서비스를 제공하는 프로세스가 업데이트 뒤 시작됐고, 이전 프로세스나 오래된 컨테이너가 남지 않았다.
3. **접근 증거:** 인터넷 직접 노출이 사라지고 승인된 관리 경로에서만 정상 기능이 동작한다.

패치 중 오류가 났는데 버전 문자열만 바뀐 경우, 다중 인스턴스 중 일부만 재기동된 경우, 롤백 이미지가 취약 버전을 다시 올리는 경우를 실패 조건으로 둔다. 고가용성 구성이라면 각 노드를 개별 자산으로 확인한다. 정상 로그인과 읽기 작업을 통한 회귀 점검은 필요하지만 인증 우회 요청을 재현하거나 공격용 쿠키를 다시 보내는 검증은 하지 않는다.

## IoC 부재와 침해 부재를 분리한다

Vates는 성공한 비인증 접근 자체가 Xen Orchestra 애플리케이션 로그에 남지 않을 수 있다고 밝힌다.[1] 공급자가 제공한 네트워크 패턴, 특정 VM 이름, IP·도메인 같은 IoC는 알려진 캠페인을 찾는 데 유용하지만 다른 공격자의 변형까지 포괄하지 않는다. 공지에도 “IoC가 없다는 것만으로 침해가 없다고 결론 내릴 수 없다”는 한계가 명시돼 있다.[1]

따라서 선별은 네 가지 축으로 진행한다.

- **접근:** 패치 전 노출 기간의 프록시·방화벽·NetFlow에서 평소와 다른 관리 API 접근과 출발지를 찾는다.
- **신원:** 관리자 계정, 인증 토큰, OTP, 디렉터리 연동과 로그인 시각의 생성·변경·사용 이력을 맞춘다.
- **제어 작업:** 예상하지 못한 VM 생성·복제·시작, 콘솔 접근, 호스트 작업, 저장소 연결 변경을 찾는다.
- **후속 행위:** 호스트의 새 계정·키·서비스·예약 작업, 비정상 프로세스와 외부 연결을 조사한다.

하나의 로그가 비어 있다고 사건을 닫지 않는다. 반대로 IoC 한 건만으로 모든 시스템이 장악됐다고 단정하지도 않는다. 관측 시각, 원본 로그, 해당 자산, 해석과 대안 설명을 분리해 기록하고, 상관관계가 확인되면 조사 범위를 인접 풀과 백업 계정으로 넓힌다.

## 확인된 침해라면 비밀 회전과 재설치가 복구 조건이다

Vates는 침해가 확인된 경우 구성 유출과 자격 증명 수집을 배제할 수 없으므로 프록시, 백업 원격지, `root` 계정과 풀 시크릿, 사용자 계정, OTP 시크릿, 메일 서버 비밀번호 등 Vates VMS가 사용하는 비밀을 회전하라고 권고한다. 또한 정리만으로 공격자가 남긴 백도어 제거를 보장할 수 없기 때문에 전체 재설치를 권고한다.[1]

회전 순서는 신뢰 경계를 고려해야 한다. 먼저 격리된 깨끗한 관리 단말과 신뢰할 수 있는 신원 시스템을 확보한다. 그다음 Xen Orchestra가 접근하던 외부 시스템의 비밀을 폐기하고 새 자격 증명의 권한을 최소화한다. 손상 가능성이 있는 관리 VM에서 새 비밀을 입력하면 다시 노출될 수 있으므로, 새로 구축해 검증한 관리면에 마지막으로 연결한다. 백업 복원도 백업 생성 시각이 침해 이전이라는 이유만으로 충분하지 않다. 복원본의 계정·작업·플러그인·연결 설정과 백업 저장소의 변경 이력을 함께 확인한다.

침해가 확인되지 않았더라도 고위험 노출 기간이 있었고 핵심 로그가 없다면 “안전 확인” 대신 “판정 불충분”으로 남긴다. 조직의 위험 수용 기준에 따라 예방적 비밀 회전이나 재구축을 선택할 수 있다. 이 결정은 공급자가 모든 환경에 요구한 사실이 아니라, 관측 공백을 고려한 조직의 운영 판단임을 기록한다.

## 종료 기준은 패치 완료와 복구 완료를 나눠 쓴다

패치 작업의 완료 조건은 모든 인스턴스가 수정선 이상이고, 이전 런타임이 사라졌으며, 관리면이 전용 경로로 제한되고, 정상 관리·백업 기능이 회귀 점검을 통과한 상태다. 침해 대응의 완료 조건은 훨씬 넓다.

- 노출 기간과 조사 대상 자산 목록이 확정됐다.
- 관리 VM, 호스트, 풀, 백업, 외부 연동의 증거가 보존·검토됐다.
- 발견된 이상 징후가 설명되거나 대응 조치와 연결됐다.
- 폐기 대상 비밀이 실제로 무효화됐고 새 비밀의 최소 권한이 확인됐다.
- 확인된 침해에서는 신뢰할 수 있는 설치 매체로 재구축했고, 재연결 순서와 복구 검증 기록이 남았다.
- 탐지 공백과 잔여 위험의 수용 주체와 재검토 날짜가 정해졌다.

CISA의 KEV 등재는 실제 악용 증거가 있다는 뜻이지만, 특정 조직이 침해됐다는 뜻은 아니다.[2] 반대로 패치 성공도 특정 조직이 침해되지 않았다는 뜻은 아니다. 이 두 문장을 분리해 운영하는 것이 가상화 관리면 사고에서 가장 중요한 복구 원칙이다.
