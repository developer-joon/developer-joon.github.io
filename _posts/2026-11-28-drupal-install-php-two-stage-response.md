Drupal 사이트에 최신 패키지를 배포했다는 사실과 그 사이트가 안전하다는 결론은 같은 말이 아니다. 2026년 11월 18일 공개된 SA-CORE-2026-017은 `install.php`가 특정 조건에서 재설치에 악용돼 사이트 탈취나 원격 코드 실행으로 이어질 수 있다고 설명했다. 영향 범위는 Drupal 10.6.22 미만, 11.0.0 이상 11.3.22 미만, 11.4.0 이상 11.4.13 미만이다. Drupal 보안팀은 실제 운영 사이트에서 11월 19일 19:00 UTC부터 악용됐다는 보고도 받았다고 공지했다.[1]

일주일 뒤 나온 SA-CORE-2026-019는 대응 기준을 다시 높였다. 첫 수정 뒤에도 비정상적이거나 불완전한 설치 상태의 일부 사이트는 탈취 위험이 남았고, 사용자 화면만으로는 그 상태를 알기 어렵다고 했다. 이 두 번째 취약점 CVE-2026-136716의 영향 범위는 Drupal 10.6.23 미만, 11.0.0 이상 11.3.23 미만, 11.4.0 이상 11.4.14 미만이다. 공지는 이 문제도 실제 악용 중이며, 패키지 갱신 후 `update.php`를 실행해 업데이트 훅까지 완료해야 한다고 명시한다.[2]

따라서 대응은 두 단계다. 먼저 취약 상태를 제거하고 설치 프로그램을 보호한다. 그다음 취약했던 기간에 이미 침해가 발생했는지 별도로 조사한다. 첫 단계가 성공해도 두 번째 단계의 결론을 대신할 수 없다.

## 1. 두 공지를 하나의 변경 작업으로 읽기

첫 공지만 기준으로 삼으면 11.4.13이나 10.6.22를 완료 버전으로 오인할 수 있다. 11월 25일 기준 목표는 지원 브랜치의 더 최신 수정판인 11.4.14, 11.3.23, 10.6.23 이상이다. Drupal 11.2 이하와 10.5 이하는 보안 지원이 끝났으므로 “해당 브랜치의 최신 버전”만 설치하는 방식으로는 종료할 수 없다.[1][2]

자산별로 최소한 다음 항목을 한 행에 모은다.

| 항목 | 기록할 값 | 판정 목적 |
|---|---|---|
| 사이트와 소유자 | 운영 URL, 서비스, 담당 팀 | 누락과 중복 방지 |
| 실제 코드 버전 | 배포 릴리스, 이미지 다이제스트, 빌드 SHA | 영향 범위 대조 |
| 설치 상태 | 정상 운영·불완전 설치·신규 설치 | 후속 공지 조건 확인 |
| 설치 경로 노출 | 외부·관리망·차단 | 공격 표면 판단 |
| 업데이트 훅 | 실행 시각, 실행 주체, 성공 기록 | 코드 교체 외 상태 수정 확인 |
| 노출 기간 | 최초 배포부터 차단·수정까지 | 로그 조사 범위 설정 |
| 지원 상태 | 지원 브랜치·EOL | 업그레이드 또는 교체 결정 |

여기서 버전 문자열은 웹 응답 헤더가 아니라 실제 배포 아티팩트와 패키지 관리 기록에서 확인한다. CDN 캐시, 다중 리전, 블루·그린 슬롯이 있으면 한 곳의 결과를 전체 환경에 일반화하지 않는다. 모든 오리진과 실행 슬롯을 같은 인벤토리에 넣고, 현재 트래픽을 받지 않는 대기 슬롯도 포함한다.

## 2. 먼저 노출을 줄이고 증거를 보존한다

패치 창을 기다리는 동안 `install.php`를 인터넷에서 계속 접근 가능하게 두면 조사 범위만 커진다. Drupal이 안내한 설치 프로그램 보호 절차를 우선 적용하고, 가능하면 리버스 프록시나 웹 서버에서 관리망만 허용한다. 단, 파일을 즉시 삭제하거나 로그를 정리하는 방식은 피한다. 변경 전 설정과 접근 로그를 보존해야 노출 기간과 의심 요청을 나중에 재구성할 수 있다.

안전한 순서는 다음과 같다.

1. 대상 사이트, 로드밸런서, 오리진, 로그 저장소의 시계를 확인하고 조사 기준 시각을 남긴다.
2. 웹·WAF·CDN·인증·Drupal 감사 로그의 보존 기간을 연장하거나 읽기 전용 위치로 복사한다.
3. 현재 웹 루트와 설정 파일의 메타데이터, 패키지 잠금 파일, 배포 이미지 다이제스트를 기록한다.
4. 승인된 제어 지점에서 `install.php` 접근을 제한한다.
5. 상태가 불명확하거나 의심 징후가 있는 노드는 로드밸런서에서 빼되 디스크를 지우지 않는다.

외부에서 공격 문자열을 보내 설치 상태를 시험할 필요는 없다. 승인된 관리망에서 평범한 `HEAD` 또는 `GET` 요청으로 차단 정책이 적용됐는지 확인하고, 응답 본문은 민감 정보가 섞이지 않도록 저장 범위를 제한한다. 이 검사는 보호 상태 확인이지 취약점 재현이 아니다.

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${SITE_URL:?set an approved HTTPS site URL}"
case "$SITE_URL" in https://*) ;; *) echo "HTTPS URL required" >&2; exit 1 ;; esac
curl --fail-with-body --silent --show-error \
  --connect-timeout 5 --max-time 15 \
  --output /dev/null --write-out '%{http_code}\n' \
  "${SITE_URL%/}/install.php"
```

이 명령은 인증 정보나 쿠키를 보내지 않는다. 기대 응답 코드는 조직 정책에 따라 403 또는 404처럼 미리 정의한다. 아직 실행하지 않은 환경에서는 “차단됐다”고 쓰지 말고 변경 검증 항목으로 남긴다.

## 3. 패키지, 데이터베이스 업데이트, 설치 프로그램 보호를 묶는다

CVE-2026-136716 대응에서 핵심은 파일 교체와 상태 업데이트를 분리하지 않는 것이다. 변경 계획에는 지원 버전으로 업그레이드, `update.php` 또는 조직이 승인한 동등한 업데이트 절차 실행, 설치 프로그램 보호가 모두 있어야 한다.[2]

운영 변경은 먼저 백업의 존재가 아니라 **복원 가능성**을 확인한 뒤 시작한다. 최근 데이터베이스 백업과 파일 백업의 생성 시각, 암호화 키 접근 권한, 복원 담당자를 확인한다. 복원 시험을 이번 긴급 변경에서 새로 수행하지 못했다면 그 사실을 위험으로 기록한다. 멀티사이트 설치라면 사이트별 데이터베이스와 설정 경계를 따로 적는다.

배포 뒤에는 다음 세 증거를 함께 남긴다.

- **아티팩트 증거:** 각 노드가 지원되는 수정 릴리스 또는 그 이후 버전을 실행한다.
- **상태 증거:** 업데이트 훅이 모든 사이트 데이터베이스에서 성공했고 미실행 항목이 없다.
- **노출 증거:** 외부 경로에서 설치 프로그램이 차단되고 관리 절차 없이 열리지 않는다.

롤링 배포에서는 새 코드가 올라왔어도 이전 PHP-FPM 프로세스나 오래된 컨테이너가 남을 수 있다. 오케스트레이터의 선언 상태만 보지 말고 실행 중인 이미지 다이제스트, 프로세스 시작 시각, 로드밸런서 대상 목록을 대조한다. 변경 중 오류율과 로그인·콘텐츠 작성·캐시 무효화 같은 핵심 기능도 관찰한다. 단순히 홈페이지가 200을 반환하는 것은 충분한 회귀 검증이 아니다.

## 4. `user 1`과 설치 경로를 중심으로 침해 흔적을 찾는다

Drupal 공지는 승인되지 않은 접근, 특히 `user 1` 계정의 예기치 않은 변경이나 그 계정이 수행한 변경을 확인하라고 권고한다. 또한 `user 1` 이메일이 조직이 통제하는 주소인지 확인하고 비밀번호 재설정을 고려하라고 한다.[2] 이 권고는 조사 시작점이지 완전한 침해 지표 목록은 아니다.

조사 시간대는 첫 취약 버전 배포 시점부터 설치 경로 차단과 후속 수정 완료 시점까지 잡는다. 그 범위에서 다음을 서로 연결한다.

- CDN·WAF·웹 서버의 `install.php` 접근 시각, 출발지, 응답 상태, 요청 식별자
- `user 1`의 이메일·암호·역할 변경과 로그인 기록
- 새 관리자 계정, 역할·권한·모듈·테마 변경
- 웹 루트와 쓰기 가능한 디렉터리에 생긴 새 PHP 파일 또는 기존 파일 변경
- PHP-FPM·웹 서버의 비정상 자식 프로세스, 예기치 않은 외부 연결, 반복 재시작
- 배포 시스템을 거치지 않은 설정과 코드 차이

접근 로그에 `install.php`가 보인다는 사실만으로 침해를 확정하지 않는다. 반대로 관련 로그가 없다고 안전을 확정하지도 않는다. 로그 보존이 짧거나 CDN과 오리진 사이에서 필드가 사라질 수 있기 때문이다. 계정·파일·프로세스·네트워크 증거가 같은 시간대에 맞물리는지 보고 신뢰도를 정한다.

의심 노드를 조사할 때는 즉석에서 파일을 삭제하거나 비밀번호만 바꾸지 않는다. 먼저 승인된 포렌식 절차로 디스크·메모리·로그의 보존 우선순위를 정한다. 운영 지속이 필요하면 깨끗한 이미지로 대체 노드를 만들고, 의심 노드는 네트워크 격리 상태로 보존하는 편이 증거와 가용성을 함께 지키기 쉽다.

## 5. 의심 징후가 나오면 복구 반경을 넓힌다

침해 가능성이 높다면 “패치 완료” 티켓에서 사고 대응 티켓으로 전환한다. 웹 노드만 재배포해도 데이터베이스에 추가된 관리자, 변조된 콘텐츠, 유출된 비밀은 남을 수 있다. 조사 범위에는 데이터베이스, 파일 저장소, 배포 자격 증명, SMTP·객체 저장소·검색·캐시 연동, 관리자 세션이 포함돼야 한다.

복구는 신뢰할 수 있는 기준 이미지와 검증된 백업을 사용한다. 침해 시점 이후 백업은 악성 변경을 포함할 수 있으므로 생성 시각만으로 선택하지 않는다. 복원 후보의 코드·구성·계정 차이를 검토하고, 노출됐을 가능성이 있는 API 키와 관리자 비밀번호는 우선순위에 따라 회전한다. 새 비밀을 의심 노드에 먼저 주입하면 다시 노출될 수 있으므로 격리와 재구축 순서를 앞세운다.

법무·개인정보·고객 통지 의무는 보유 데이터와 관할에 따라 달라진다. 기술 팀이 로그 몇 줄만 보고 “유출 없음”을 선언하지 말고, 사고 대응 책임자에게 확인된 사실·확인 불가 영역·보존 실패를 분리해 전달해야 한다.

## 6. 종료 조건은 두 개로 나눈다

첫 번째 종료 조건은 **취약 상태 제거**다. 모든 자산이 지원되는 후속 수정 버전 이상이고, 업데이트 훅이 완료됐으며, `install.php`가 승인되지 않은 네트워크에서 차단되고, 오래된 실행 인스턴스가 트래픽에서 빠졌다는 증거가 있어야 한다.

두 번째 종료 조건은 **침해 평가 완료**다. 조사 기간이 정의됐고, 필요한 로그와 계정·파일·프로세스 증거를 검토했으며, 발견 사항의 처리와 남은 가시성 공백이 승인돼야 한다. 증거 부족은 “침해 없음”이 아니라 “판정 제한”이다. 의심 징후가 있었다면 깨끗한 재구축, 비밀 회전, 지속 관찰까지 완료한 뒤 종료한다.

이번 사건의 교훈은 간단하다. 패치는 취약한 문을 닫는 작업이고, 침해 조사는 그 문이 열려 있던 동안 누가 들어왔는지 확인하는 작업이다. Drupal의 두 연속 공지는 두 작업을 한 변경 계획 안에 넣되, 완료 판정은 끝까지 분리해야 한다는 사례다.
