“GitHub Copilot과 Claude를 활용해 개발했습니다.” 이제 이 문장만으로는 지원자의 역량을 거의 알 수 없다. 어떤 문제를 맡겼는지, 결과가 틀렸을 때 알아챌 수 있었는지, 보안과 비용의 경계를 누가 정했는지가 빠져 있기 때문이다. 도구 이름은 사용 경험을 말하지만 판단 능력을 증명하지 않는다.

JetBrains의 2026 개발자 생태계 조사는 2026년 5~7월 198개 국가·지역의 개발자 2만 8,945명을 분석했다. 경력 1~2년 응답자의 60%는 AI 생성 결과가 자신의 결과보다 낫다고 평가했고, 경력 16년 이상에서는 47%였다. 보고서는 숙련자가 지침·명세·검증 절차를 더 많이 제공한다고도 설명한다.[1][2] 이 차이는 세계 온라인 설문의 집단 간 연관이다. AI를 많이 쓰면 실력이 낮아진다거나, 검증 기록을 만들면 채용된다는 인과 증거가 아니다. 지역·고용상태·언어 사용 등을 가중하고 JetBrains 사용자 편향을 보정했어도 자가보고 편향은 남는다.

이 글에서 제안하는 포트폴리오 형식은 공식 채용 기준이 아니라 **저자의 실무 제안**이다. 목표는 AI 사용을 숨기거나 과장하는 것이 아니라, 채용 담당자가 “이 지원자에게 결과물의 책임을 맡길 수 있는가”를 확인할 재현 가능한 자료를 제공하는 데 있다. 취업을 보장하지는 않지만, 모호한 도구 목록보다 구체적인 대화를 가능하게 한다.

## 1. 프롬프트보다 먼저 문제 계약을 보여준다

좋은 기록은 채팅 전문이 아니라 작업 전의 계약에서 시작한다. 프로젝트 README에 `문제`, `제약`, `수용 기준`, `금지 조건` 네 칸을 둔다. 예를 들어 “CSV 업로드 기능 구현” 대신 다음처럼 쓴다.

- 문제: 운영자가 최대 10만 행의 주문 CSV를 업로드한다.
- 제약: 개인정보 원문을 외부 모델에 전송하지 않으며, 메모리 512MB 안에서 처리한다.
- 수용 기준: 정상 파일 처리율 100%, 잘못된 행 번호 표시, 같은 파일 재시도 시 중복 주문 0건.
- 금지 조건: 부분 실패를 성공으로 표시하지 않고, 로그에 이메일·전화번호를 남기지 않는다.

그다음 AI에 보낸 핵심 입력과 모델·도구 버전, 사람이 추가한 전제, 채택하지 않은 제안을 요약한다. 모든 대화를 무가공으로 공개할 필요는 없다. 회사 코드나 개인정보가 섞인 로그를 공개하면 오히려 판단 경계가 없다는 신호가 된다. 공개용에는 민감정보를 제거한 최소 재현 예시를 만들고, 왜 축약했는지 적는다.

`prompt.md` 하나에 멋진 지시문을 모으는 방식도 충분하지 않다. 같은 문장을 다른 시점의 모델에 넣으면 결과가 달라질 수 있고, 프롬프트만으로 요구사항 해석이 맞았는지 알 수 없다. 대신 `spec.md`에 사람이 승인한 불변 조건을, `ai-log.md`에 주요 상호작용과 선택 이유를, 테스트에 기계적으로 확인 가능한 조건을 둔다. 포트폴리오의 중심을 대화 기술이 아니라 문제 정의와 수용 기준으로 옮기는 것이다.

## 2. 생성 결과를 통과시킨 검증 사다리를 남긴다

Stack Overflow의 2026 개발자 설문은 AI 도구 사용과 신뢰를 별개로 다룬다. 설문 결과는 전 세계 응답자의 인식 자료이지 특정 지원자의 능력이나 한국 채용담당자의 선호를 측정한 값이 아니다.[3] 따라서 “AI가 유용하다는 사람이 많다”를 자기 코드의 품질 근거로 쓰면 안 된다. 품질은 프로젝트 안의 검증으로 입증해야 한다.

검증은 값싼 단계에서 비싼 단계로 올린다. 먼저 formatter와 정적 분석, 단위 테스트를 실행한다. 다음으로 데이터베이스·외부 API를 포함한 통합 테스트, 실패 주입, 성능 측정, 의존성·비밀정보 검사를 한다. 마지막에는 사람이 변경 diff를 읽고 도메인 규칙과 운영 위험을 검토한다. 각 단계의 명령, 입력 fixture, 실제 결과를 저장한다.

```text
검증 기록 예시
commit: 8f2c...
생성 범위: parser 초안과 테스트 case 후보
사람의 변경: streaming 처리, idempotency key, 오류 메시지
실행: pytest -q / ruff check / pip-audit
결과: 42 passed, 정적 분석 0건, 취약점 0건
미해결: 100만 행에서 처리시간 목표 초과
판정: 10만 행 범위만 수용, 대용량은 후속 이슈로 분리
```

여기서 숫자는 실제 실행 결과여야 한다. 스크린샷보다 CI 링크나 텍스트 로그가 재검증하기 쉽다. 다만 “테스트 42개 통과”도 품질의 완전한 증명은 아니다. 어떤 위험을 테스트하지 않았는지, fixture가 실제 데이터를 얼마나 대표하는지 함께 적어야 한다. 실패한 명령을 지우지 말고 수정 전후를 연결하면 문제 발견 능력과 복구 과정을 보여줄 수 있다.

## 3. 실패 사례를 포트폴리오의 핵심 산출물로 만든다

완벽한 생성 기록만 있는 프로젝트는 믿기 어렵다. 실제 AI 보조 개발에서는 존재하지 않는 API, 오래된 패키지 사용법, 과도한 예외 삼키기, 경계값 누락이 나온다. 한두 개의 대표 실패를 골라 `decision-log/`에 남긴다.

각 기록은 다섯 질문에 답하면 된다. 첫째, 무엇을 기대했는가. 둘째, 실제로 어떤 실패가 관찰됐는가. 셋째, 어떤 테스트나 문서로 실패를 확인했는가. 넷째, AI 제안을 폐기·수정·채택한 기준은 무엇인가. 다섯째, 같은 실패를 다시 막기 위해 무엇을 자동화했는가. 예컨대 모델이 모든 CSV를 메모리에 읽도록 제안했다면 10만 행 fixture에서 메모리를 측정하고, iterator 방식으로 바꾸고, 최대 RSS 회귀 테스트를 추가한 흐름을 보여준다.

중요한 것은 AI가 틀렸다는 사실을 과시하는 것이 아니다. 사람도 틀린다. 핵심은 오류가 사용자에게 도달하기 전에 잡히는 구조와 최종 승인자가 누구인지다. AI가 낸 보안 수정안을 다른 AI에게 다시 묻고 끝냈다면 독립 검증이 아니다. 공식 문서, 실제 실행, 정적 분석 결과와 사람이 읽은 diff처럼 서로 다른 근거를 결합한다.

실패를 공개할 때는 범위를 정직하게 제한한다. “SQL injection을 완전히 방지했다” 대신 “이 엔드포인트에서 문자열 조합을 제거했고, 세 가지 공격 fixture와 정적 분석을 통과했다”고 쓴다. 검증한 범위와 남은 범위를 분리하면 과장 없이 책임감을 드러낼 수 있다.

## 4. 기여도를 파일 수가 아니라 판단 단위로 나눈다

면접에서 “몇 퍼센트를 AI가 작성했나요?”라는 질문을 받을 수 있다. 줄 수 비율은 쉽게 계산되는 듯하지만 유용하지 않다. 생성 후 전부 고쳤을 수도 있고, 짧은 설정 한 줄이 보안 경계를 결정할 수도 있다. 다음 네 층으로 답하는 편이 낫다.

1. **AI가 제안한 것:** 초기 구조, 반복 코드, 테스트 아이디어.
2. **사람이 결정한 것:** 데이터 모델, 오류 정책, 개인정보 경계, 수용 기준.
3. **사람이 검증한 것:** 문서 대조, 테스트, 성능·보안 검사, 코드리뷰.
4. **남아 있는 불확실성:** 미측정 부하, 특정 플랫폼 호환성, 운영 데이터 부족.

커밋도 이 경계를 따라 작게 나눈다. `AI 초안 생성`이라는 거대한 커밋보다 `parser baseline`, `reject malformed rows`, `add idempotency test`, `stream large files`처럼 판단과 검증이 보이는 단위가 낫다. Pull request 본문에는 생성 도구를 밝혀도 되지만, 변경 목적·위험·실행 결과가 먼저 와야 한다.

면접에서는 도구를 옹호하거나 변명하지 않는다. “AI를 썼지만 제가 다 확인했습니다” 대신 가장 위험했던 제안 하나, 그것을 잡은 신호, 수정한 기준, 아직 확신하지 못하는 지점을 설명한다. 이는 공식 면접 정답이 아니라 저자의 실무 제안이다. 회사마다 AI 사용 정책과 평가 방식이 다르므로 공고와 면접 안내를 우선한다.

## 5. 공개 저장소를 15분 검토 가능한 구조로 만든다

채용 담당자가 긴 로그를 전부 읽는다고 가정하지 않는다. 저장소 첫 화면에서 15분 안에 증거를 따라갈 수 있게 만든다.

```text
README.md                 문제, 데모, 본인 기여, 한계
spec.md                   제약과 수용 기준
decision-log/001.md       대표 실패와 수정 판단
tests/                    수용 기준에 연결된 자동 테스트
.github/workflows/ci.yml  재실행 가능한 검증
SECURITY.md               데이터·비밀정보·의존성 경계
```

README의 각 주장에는 링크를 붙인다. “대용량 처리” 옆에는 benchmark 조건과 결과를, “안전한 업로드” 옆에는 허용 확장자·크기 제한 테스트를 연결한다. 실행 환경이 사라질 수 있으므로 의존성 lockfile, seed data, 명령을 제공한다. 비용이 드는 외부 모델 없이도 핵심 테스트를 재실행할 수 있게 응답 fixture나 mock을 둔다. 모델 출력 자체를 golden truth로 고정하기보다 파싱 계약과 안전 조건을 고정한다.

공개 전에 비밀정보 검색, 라이선스 확인, 생성 코드의 출처 검토를 한다. 외부 저장소 코드를 모델이 재현했는지 확신할 수 없다면 해당 부분을 직접 다시 작성하거나 적절한 라이선스 근거를 확인한다. “AI가 만들었다”는 말은 저작권·보안 책임을 외부로 넘겨주지 않는다.

## 6. 제출 전 체크리스트: 사용량이 아니라 책임을 압축한다

최종 점검은 간단하다. 요구사항과 수용 기준이 연결돼 있는가. 실행 가능한 테스트와 최근 CI 결과가 있는가. 대표 실패와 수정 이유가 있는가. AI 제안과 본인 결정을 구분했는가. 개인정보·회사 자산·비밀정보를 제거했는가. 성능 수치에 환경과 입력 크기가 있는가. 미해결 위험을 숨기지 않았는가. README의 모든 큰 주장을 저장소 안의 증거로 추적할 수 있는가.

이 구조는 취업을 보장하는 요령이 아니다. JetBrains와 Stack Overflow의 설문도 한국 기업의 채용 기준을 직접 측정하지 않는다.[1][3] 다만 AI 시대의 포트폴리오에서 더 중요한 질문을 선명하게 만든다. 얼마나 많이 생성했는지가 아니라, 무엇을 요구했고, 어디까지 믿었고, 어떻게 틀림을 발견했으며, 최종적으로 누가 책임졌는가다. 프롬프트는 그 과정의 입력 하나일 뿐이다. 채용 증거가 되는 것은 검증 가능한 판단의 연쇄다.
