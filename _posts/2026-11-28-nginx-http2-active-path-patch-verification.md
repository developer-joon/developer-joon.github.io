NGINX 버전이 취약 범위에 있다는 사실만으로 모든 서버의 위험이 같지는 않다. 반대로 패키지 목록이 최신이라는 사실만으로 실제 요청 경로가 수정됐다고 말할 수도 없다. 2026년 11월 18일 공개된 HTTP/2 관련 두 취약점은 모두 데이터 플레인의 메모리 안전 문제지만, 도달 조건이 다르다.

CVE-2026-123007은 HTTP/2 흐름 제어 처리에서 윈도 크기가 허용 한계를 넘을 때 힙 버퍼 오버플로가 발생할 수 있는 문제다. F5 공지는 NGINX Open Source 1.9.5~1.30.6과 1.31.0~1.31.8을 취약 범위로, 1.30.7과 1.31.9를 수정이 도입된 버전으로 제시한다. 반면 nginx.org 공식 보안 목록은 취약 범위를 0.6.18~1.31.8로 적어 하한이 충돌한다. NGINX Plus 37 계열은 세부 포인트 릴리스가 따로 제시되므로 오픈소스 번호를 그대로 적용하면 안 된다.[1]

CVE-2026-123633은 클라이언트 측 HTTP/2를 사용하고 요청을 백엔드로 프록시하며 워커의 `worker_connections` 여유가 낮은 조건에서 use-after-free가 발생할 수 있는 문제다. F5 공지는 Open Source 1.19.7~1.30.6과 1.31.0~1.31.8을 취약 범위로 적지만, nginx.org 공식 보안 목록의 하한은 1.25.0이다. Open Source 수정선은 1.30.7과 1.31.9로 제시되지만, NGINX Plus·Instance Manager·WAF·Gateway Fabric·Ingress Controller 등 파생 제품의 영향 및 수정 버전은 제품별로 다르다.[2][3]

두 공식 출처의 Open Source 하한은 CVE별로 다음처럼 다르다.

| CVE | F5 advisory의 취약 범위 | nginx.org의 취약 범위 | 공급자 정정 전 판정 |
|---|---|---|---|
| CVE-2026-123007 | 1.9.5~1.30.6, 1.31.0~1.31.8 | 0.6.18~1.31.8 | 더 보수적인 0.6.18 하한을 적용한다. 특히 0.6.18~1.9.4는 비영향으로 닫지 않고 업그레이드 대상으로 둔다. |
| CVE-2026-123633 | 1.19.7~1.30.6, 1.31.0~1.31.8 | 1.25.0~1.31.8 | 1.19.7~1.24.x를 출처 충돌로 판정 보류하고 업그레이드 또는 공급자의 명시적 확인이 끝날 때까지 비영향으로 닫지 않는다. |

이 표는 버전 판정을 위한 fail-closed 규칙이다. 두 출처가 충돌하면 범위의 합집합을 우선 격리·패치 대상으로 삼고, 제품·빌드·백포트 상태가 불명확한 자산도 `unaffected`가 아니라 `판정 보류`로 기록한다. 고정 상한과 수정 버전은 변경 시점에 두 CVE의 F5 advisory와 nginx.org 현재 표를 각각 다시 확인해야 한다.[1][2][3]

핵심은 “NGINX가 있는가”가 아니라 “어떤 제품과 바이너리가 어느 요청 경로에서 HTTP/2를 처리하는가”를 찾는 것이다.

## 1. CVE 이름보다 데이터 경로를 먼저 그린다

두 취약점 모두 F5가 제어면 노출이 아닌 데이터면 문제라고 설명한다.[1][2] 그래서 관리 콘솔이 외부에 없다는 사실은 면제 조건이 아니다. 인터넷 클라이언트에서 CDN, 로드밸런서, 인그레스, 사이드카, 애플리케이션 프록시, 백엔드로 이어지는 흐름을 그리고 각 홉의 프로토콜과 구현체를 적어야 한다.

예를 들어 외부 CDN에서 HTTP/2를 종료하고 오리진에는 HTTP/1.1만 보낼 수도 있다. 반대로 CDN 뒤의 Kubernetes Ingress가 다시 HTTP/2를 수신하거나 NGINX가 gRPC를 처리할 수 있다. TLS 설정만 보고 판단하면 평문 `h2c`, 내부 리스너, 별도 가상 서버를 놓친다.

인벤토리 한 행에는 다음을 기록한다.

| 항목 | 예시가 아닌 실제 기록값 | 이유 |
|---|---|---|
| 서비스·환경 | 결제 API 운영, 사내 개발 등 | 변경 우선순위 지정 |
| 홉과 역할 | edge, ingress, sidecar, reverse proxy | 중복 자산 구분 |
| 제품 | Open Source, Plus, Gateway Fabric 등 | advisory 표 선택 |
| 실행 버전 | 전체 버전·빌드 문자열 | 영향 범위 대조 |
| 아티팩트 | 패키지 릴리스·이미지 다이제스트 | 태그 재사용 방지 |
| 수신 프로토콜 | HTTP/2 TLS, h2c, HTTP/1.1 | 도달 가능성 확인 |
| 업스트림 경로 | proxy·gRPC·정적 응답 | CVE-2026-123633 조건 구분 |
| 노출 범위 | 인터넷·파트너망·내부 | 패치 순서와 격리 결정 |
| 워커 상태 | PID·시작 시각·세대 | 새 바이너리 적용 확인 |

CMDB의 제품명만으로는 부족하다. 컨테이너 이미지 속 NGINX, 애플리케이션 번들, 어플라이언스에 포함된 파생 구성요소가 따로 있을 수 있다. 공급자 advisory에서 “연구 중” 또는 수정판 없음으로 표시된 제품은 Open Source 패키지만 임의 교체하지 말고 해당 제품의 지원 경로를 따른다.[1][2]

## 2. 읽기 전용 확인으로 활성 HTTP/2 경로를 좁힌다

먼저 선언 설정과 실행 상태를 나눠 수집한다. `nginx -T`는 병합된 설정을 보여 줄 수 있지만 인증서 경로, 내부 호스트명, 업스트림 구조가 포함될 수 있다. 출력 전체를 티켓이나 채팅에 붙이지 말고 승인된 호스트의 제한된 저장소에 보관한 뒤 필요한 지시어만 검토한다. 컨테이너에서는 이미지 파일과 실행 컨테이너의 설정이 다를 수 있으므로 양쪽을 혼동하지 않는다.

확인 대상은 HTTP/2 리스너, 프록시·gRPC 경로, `worker_connections`, 실제 바이너리 경로와 빌드 옵션이다. 다만 CVE-2026-123633은 단순히 설정값이 작다는 이유만으로 도달 가능하다고 단정할 수 없다. 공식 공지가 제시한 클라이언트 HTTP/2, 백엔드 프록시, 낮은 연결 여유라는 조건을 자산별로 함께 평가한다.[2]

승인된 정상 엔드포인트에서 프로토콜 협상만 확인하려면 자격 증명 없는 상태 검사 URL을 사용한다.

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${HEALTH_URL:?set an approved public health URL}"
case "$HEALTH_URL" in https://*) ;; *) echo "HTTPS URL required" >&2; exit 1 ;; esac
curl --silent --show-error --fail \
  --http2 --connect-timeout 5 --max-time 15 \
  --output /dev/null --write-out 'http_version=%{http_version} code=%{http_code}\n' \
  "$HEALTH_URL"
```

이 명령은 특수 트래픽이나 취약점 재현이 아니라 정상 요청의 협상 결과만 확인한다. 프록시 체인에서는 최종 응답의 HTTP 버전이 내부 각 홉의 프로토콜을 증명하지 않는다. 내부 경로는 설정, 서비스 메시 원격 측정, 로드밸런서 구성으로 별도 확인한다. 아직 실행하지 않았다면 결과를 추정하지 말고 검증 계획으로 남긴다.

## 3. 제품별 수정선을 섞지 않는다

Open Source의 공통 수정 기준은 1.30.7 또는 1.31.9 이상이지만, 이것만 표준 답안으로 배포하면 파생 제품을 놓친다. CVE-2026-123633 공지는 NGINX Instance Manager 2.25.0, F5 WAF for NGINX 5.16.2 또는 5.14.4, F5 DoS for NGINX 4.13.0, NGINX Gateway Fabric 2.9.0, Ingress Controller의 2026-lts-r11 또는 5.8.0 등 제품별 수정선을 제시한다. 일부 구버전 계열에는 수정 후보가 없다고 표시한다.[2]

CVE-2026-123007과 CVE-2026-123633의 Plus 수정 포인트도 같지 않다. 따라서 한 CVE의 “수정됨”을 다른 CVE에 재사용하지 않는다. 제품, 브랜치, 현재 버전, 두 CVE 각각의 상태, 목표 버전, 근거 URL을 열로 둔 패치 매트릭스를 만든다.

공급자 패키지나 어플라이언스가 NGINX를 내장했다면 내부 버전 문자열만으로 자의적으로 안전 판정을 하지 않는다. 벤더가 백포트를 적용했을 수 있고, 반대로 보이는 버전이 같아도 수정이 없을 수 있다. 공급자의 제품별 advisory와 빌드 번호를 우선한다. 지원이 끝난 계열이나 수정판이 없는 계열은 외부 노출을 줄이고 지원 브랜치로 이동하는 결정을 별도 위험 승인으로 관리한다.

패치 전에는 설정 검사, 롤백 아티팩트, 용량 여유, 세션 영향, 헬스 체크 기준을 준비한다. 메모리 손상 취약점의 “완화책 없음” 표기는 설정 튜닝만으로 결함을 제거할 수 없다는 뜻이다.[1][2] HTTP/2 임시 비활성화가 가능한 환경이라도 기능·성능 영향과 우회 리스너를 검토해야 하며, 이를 패치 완료로 기록해서는 안 된다.

## 4. 무중단 재적용보다 새 워커 증명이 중요하다

NGINX는 설정 재로드와 바이너리 업그레이드의 동작이 다르다. 파일 시스템의 실행 파일만 교체하고 기존 워커가 계속 떠 있으면 트래픽은 구 코드로 처리될 수 있다. 컨테이너에서도 새 이미지를 푸시했지만 Deployment가 이전 다이제스트를 실행하거나, 일부 Pod가 업데이트되지 않은 상태가 남을 수 있다.

배포 후 다음 세 층을 대조한다.

1. **공급망 층:** 승인된 패키지·이미지의 정확한 버전과 다이제스트
2. **배포 층:** 각 인스턴스·Pod·노드가 참조하는 실제 아티팩트
3. **프로세스 층:** 요청을 받는 master와 worker의 PID, 시작 시각, 실행 파일

롤링 업데이트는 최대 동시 중단 수, 연결 드레이닝, 재시도 폭증을 고려해 작은 묶음부터 진행한다. 각 묶음에서 정상 HTTP/1.1·HTTP/2·gRPC 등 그 서비스가 실제 제공하는 경로를 검증한다. 공격 트래픽을 만들지 말고 기존 합성 모니터와 평범한 상태 요청을 사용한다.

완료 증거에는 “배포 성공” 화면 대신 노드별 이미지 다이제스트 또는 패키지 빌드, 워커 시작 시각, 설정 검사 결과, 트래픽 복귀 시각을 남긴다. 오토스케일 그룹과 재해복구 이미지를 함께 갱신하지 않으면 다음 확장이나 장애 조치 때 취약 버전이 되살아날 수 있다. 골든 이미지, Helm chart, IaC 잠금 파일까지 같은 변경 범위에 넣는다.

## 5. 크래시와 재시작은 신호이지 판결이 아니다

CVE-2026-123007은 일반적으로 워커 segmentation fault로 이어질 수 있고, CVE-2026-123633도 서비스 거부나 코드 실행 가능성이 제시된다.[1][2] 따라서 패치 전 노출 기간의 워커 비정상 종료, core dump, 컨테이너 재시작, 502·503 증가, 연결 수 고갈을 시간축으로 모은다.

그러나 워커 크래시는 잘못된 모듈, 용량 부족, 운영 오류에서도 발생한다. 특정 CVE 악용으로 바로 단정하지 않는다. 반대로 크래시가 없다고 안전을 확정할 수도 없다. 다음 신호를 함께 비교한다.

- 평소 기준선을 벗어난 worker exit와 segmentation fault
- 같은 시점의 HTTP/2 연결·오류·재시도 변화
- 오케스트레이터의 OOM·재시작·노드 이동 기록
- 배포되지 않은 실행 파일·모듈·설정 변경
- NGINX 계정에서 시작된 예기치 않은 자식 프로세스나 외부 연결
- WAF·CDN·로드밸런서의 비정상 요청 집중과 공통 상관 ID

로그를 조사 시스템으로 옮길 때 헤더·쿠키·쿼리의 비밀과 개인정보를 최소화한다. 원본 보존 위치와 분석용 사본을 분리하고 접근자를 기록한다. 침해 가능성이 있으면 해당 인스턴스를 트래픽에서 격리하되 재시작과 이미지 삭제를 서두르지 않는다. 휘발성 증거 보존 여부는 사고 대응 절차에 따라 결정한다.

기준일에 “악용 보도를 인지했다”는 공급자 표현이 있더라도 독립 검증된 실제 악용과 같은 말로 쓰면 안 된다. 이 글의 운영 우선순위는 메모리 안전 영향, 인터넷 노출, 공식 영향 범위에 근거한다. KEV 등재 여부나 소셜 미디어 주장으로 세부 도달 조건을 덧붙이지 않는다.

## 6. 종료는 버전·경로·프로세스·관찰로 판정한다

패치 티켓은 다음 질문에 모두 답할 때 닫는다.

- 모든 NGINX 제품과 내장 배포를 찾았는가?
- 각 자산에 해당하는 개별 advisory의 영향 범위와 수정선을 적용했는가?
- HTTP/2를 실제 처리하는 외부·내부 경로와 프록시 조건을 확인했는가?
- 트래픽을 받는 모든 워커가 수정 아티팩트에서 시작됐는가?
- 오토스케일·재해복구·대기 환경의 오래된 이미지도 제거했는가?
- 정상 프로토콜 경로의 회귀 검사와 오류율 관찰을 완료했는가?
- 패치 전 노출 기간의 이상 신호를 검토하고 가시성 공백을 기록했는가?

버전, 활성 경로, 실행 프로세스 가운데 하나라도 빠지면 “패키지는 최신인데 서비스는 취약”한 상태가 남는다. 이번 NGINX 공지는 CVSS 숫자를 보는 것보다 데이터 경로를 그리는 일이 먼저이며, 수정의 마지막 증거는 저장소의 패키지가 아니라 실제 요청을 처리하는 새 워커라는 점을 보여 준다.
