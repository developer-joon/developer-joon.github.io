GitHub는 2026년 11월 9일 GitHub Actions 워크플로 로그를 secret scanning 대상으로 추가하는 기능을 **공개 미리보기(public preview)**로 발표했다.[1] 완료된 워크플로 실행의 로그에서 지원되는 공급자 패턴을 찾고, 발견 결과를 저장소의 기존 secret scanning 경보 목록에 표시하며 해당 Actions 로그로 연결한다.[1] 유용한 탐지면이 하나 늘었지만 일반 가용(GA) 기능으로 표현해서는 안 된다.

미리보기는 기본 비활성이다. GitHub Enterprise Cloud에서 GitHub Secret Protection 또는 GitHub Advanced Security를 사용하는 엔터프라이즈가 대상이며, 엔터프라이즈 소유자가 정책을 켜야 한다. 해당 라이선스 아래에서 secret scanning이 활성화된 저장소에만 적용된다.[1] 설정 화면의 토글 하나가 보인다는 사실과 모든 저장소의 모든 로그가 검사된다는 사실은 다르다.

## 코드 스캔과 로그 스캔은 시간축이 다르다

일반적인 secret scanning은 저장소의 모든 브랜치와 전체 Git 기록에서 알려진 비밀 형식을 찾고, 이슈·풀 리퀘스트·Discussion·Wiki 등 비코드 표면도 검사한다.[2] Actions 로그 스캔은 워크플로 실행이 끝난 뒤 로그를 검사한다.[1] 즉, 커밋 전에 유출을 막는 통제가 아니라 실행 중 로그에 나타난 비밀을 사후 발견하는 통제다.

이 차이는 대응 목표를 바꾼다.

| 통제 | 주된 시점 | 막거나 찾는 것 | 한계 |
|---|---|---|---|
| push protection | 커밋·푸시 전후 | 코드에 들어가는 알려진 비밀 | 모든 로그 출력과 런타임 생성값을 보지 못함 |
| 저장소 secret scanning | 저장소 기록·비코드 표면 | 이미 저장된 비밀 | 외부 CI·런타임 로그는 별도 범위 |
| Actions 로그 스캔 미리보기 | 실행 완료 후 | 지원되는 공급자 패턴의 로그 노출 | 실시간 차단이 아니며 여러 탐지 공백이 있음 |
| Actions 마스킹 | 로그 출력 시 | 알려진 값의 원문 표시 축소 | 값 등록·변형·파생 출력에 의존하며 회전을 대신하지 않음 |

따라서 로그 스캔을 켰다고 워크플로의 최소 권한, 마스킹, 출력 검토, 짧은 수명 자격 증명, OIDC 전환을 생략할 수 없다. 이미 출력된 비밀을 뒤늦게 찾는 기능이지 노출 자체를 방지하는 안전망은 아니다.

## 공개 미리보기의 탐지 공백을 그대로 기록한다

GitHub 발표에는 현재 범위가 명확히 적혀 있다.[1]

- 기능을 활성화한 뒤 **완료된** 워크플로 실행만 검사하며 기존 로그는 백필하지 않는다.
- generic 패턴, custom 패턴, AI가 감지하는 비밀은 대상이 아니다.
- GitHub Actions가 이미 마스킹한 값은 탐지하지 않는다.
- 공개 미리보기 동안 Actions 로그에서 발생한 경보는 알림을 보내지 않는다.

“마스킹된 값은 탐지하지 않는다”는 것이 곧 취약점은 아니다. 원문이 로그에 표시되지 않았다면 노출 표면이 줄어든다. 다만 마스킹 성공과 자격 증명 안전을 같은 것으로 보지 않는다. 값이 다른 단계의 아티팩트, 캐시, 외부 로그 수집기, 디버그 출력에 남을 수 있고, 일부 변형이 마스킹을 피할 수도 있다. 로그 스캔이 경보를 만들지 않았다는 사실만으로 비밀이 없었다고 결론 내릴 수 없다.

알림이 없다는 제한은 운영상 특히 크다. 담당자가 경보 목록을 직접 확인하지 않으면 탐지는 존재하지만 대응이 시작되지 않는다. 공개 미리보기 동작은 변경될 수 있으므로 정책 문서에 확인 날짜와 문서 링크를 남기고, GA 전환이나 범위 변경 때 다시 검토한다.

## 활성화 여부는 엔터프라이즈부터 저장소까지 읽어 본다

설정은 엔터프라이즈 소유자가 **Policies → Advanced Security → Secret scanning for Actions workflow logs**에서 모든 저장소 정책을 Enabled로 선택하는 방식으로 안내됐다.[1] 하지만 적용 판정에는 여러 조건이 있다.

1. 대상이 GitHub Enterprise Cloud 또는 데이터 레지던시를 사용하는 GHE.com 엔터프라이즈인가?
2. GitHub Secret Protection 또는 GitHub Advanced Security 라이선스가 적용되는가?
3. 엔터프라이즈 정책에서 Actions 로그 스캔이 활성화됐는가?
4. 각 대상 저장소에서 secret scanning 자체가 활성화됐는가?
5. 정책 활성화 뒤 새 워크플로 실행이 실제로 완료됐는가?

이 목록은 현재 공개 문서의 조건을 운영 점검표로 풀어 쓴 것이다. 엔터프라이즈 설정을 작성했다는 사실보다 실제 저장소에서 경보 표면과 정책 상태를 읽어 확인하는 것이 중요하다. 예외 저장소, 포크, 이전된 저장소, 라이선스가 빠진 저장소를 별도 목록으로 관리한다.

역할도 분리한다. 엔터프라이즈 소유자는 정책을 켜고, 저장소 보안 담당자는 경보를 검토하며, 비밀 소유 팀은 폐기·회전하고, 워크플로 소유자는 노출 원인을 수정한다. 한 사람에게 모든 권한을 주기보다 경보가 담당 팀으로 전달되는 티켓 흐름을 만든다.

## 안전한 검증은 실제 자격 증명을 사용하지 않는다

운영 자격 증명이나 새로 발급한 테스트 토큰을 로그에 출력해 기능을 시험하면 안 된다. 공급자가 문서화한 폐기된 테스트 값이 있고 현재 미리보기의 지원 공급자 패턴에 포함되는 경우에만, 별도의 비프로덕션 저장소와 전용 워크플로에서 사용할 수 있다. 그런 값이 준비되지 않았다면 기능을 “검증했다”고 쓰지 말고 설정 상태 확인까지만 기록한다.

안전 검증 계획에는 다음 경계가 필요하다.

- 비프로덕션 엔터프라이즈 또는 제한된 테스트 저장소
- 실제 시스템 권한이 전혀 없는 폐기된 공급자 테스트 값
- 정책 활성화 시각 이후 시작해 완료된 단일 워크플로
- 최소 로그 보존 기간과 제한된 저장소 접근 권한
- 경보 목록을 확인할 담당자와 테스트 종료 후 정리 절차

예상 결과는 “지원 공급자 패턴의 테스트 값이 들어간 완료 로그가 경보 목록에 표시되고 원본 실행으로 연결된다”다.[1] 이 글에서는 그러한 테스트를 실행하지 않았으므로 실제 탐지 성공을 주장하지 않는다. 조직에서 수행할 때는 실행 ID, 완료 시각, 정책 상태, 경보 생성 시각, 경보 링크를 기록한다.

공백 검증도 공격적으로 비밀을 만들 필요가 없다. 활성화 이전 실행이 백필되지 않는지, 알림이 오지 않는지, 마스킹된 값이 경보 대상에서 제외되는지는 문서의 현재 계약으로 기록하고 운영상 보완 통제를 둔다. 실제 값으로 각각 재현해 “실패를 증명”하려 하지 않는다.

## 알림이 없는 동안은 경보 조회를 운영 작업으로 만든다

공개 미리보기에서는 Actions 로그 경보 알림이 발송되지 않는다.[1] 따라서 저장소 보안 탭의 secret scanning 경보 목록을 정기적으로 확인하는 담당자와 주기를 정해야 한다. 대규모 엔터프라이즈라면 현재 제공되는 공식 API나 내보내기 기능의 지원 범위를 문서에서 별도 확인한 뒤 중앙 티켓으로 연결한다. 지원 여부를 확인하지 않은 API 경로나 필드를 가정해 자동화를 만들면 안 된다.

운영 대시보드에는 최소한 다음 상태가 필요하다.

- 마지막 경보 조회 시각과 조회 주체
- 미처리 Actions 로그 경보 수
- 비밀 공급자와 저장소·워크플로 소유 팀
- 최초 노출·발견·폐기·회전 시각
- 비밀 사용 로그 검토 상태
- 원인 수정과 재발 방지 변경 상태
- 경보 종료 사유와 검토자

경보 수가 0인 것과 조회가 실행되지 않은 것을 구분한다. 조회 실패, 권한 부족, API 제한은 “0건”이 아니라 관측 실패다. 알림 기능이 생기더라도 정기 조회를 바로 없애지 말고 누락률을 비교한 뒤 전환한다.

## 경보가 뜨면 로그 삭제보다 폐기·회전이 먼저다

GitHub 문서는 노출된 자격 증명을 유효한 것으로 간주하고 즉시 회전할 것을 권고한다. 토큰을 삭제하고 새 토큰을 만들며, 이전 토큰을 사용하는 서비스들을 갱신하고 공급자 보안 로그에서 무단 활동을 확인해야 한다.[2][3] 로그에서 문자열을 지우거나 워크플로 실행을 삭제해도 이미 본 사람이 사용할 가능성은 사라지지 않는다.

대응 순서는 다음처럼 잡을 수 있다.

1. 경보의 저장소, 실행, 작업, 단계와 비밀 공급자를 확인한다.
2. 비밀 소유자를 호출하고 공급자 측에서 기존 비밀을 즉시 폐기한다.
3. 발급·사용 로그를 노출 시점부터 검토하고 이상 행위를 별도 사고로 분리한다.
4. 새 비밀은 최소 권한과 짧은 만료로 발급하거나 가능하면 OIDC 등 장기 비밀 없는 방식으로 전환한다.
5. 워크플로와 사용하는 서비스를 새 자격 증명으로 갱신한다.
6. 노출 원인인 디버그 출력, 잘못된 환경 변수 확장, 아티팩트 업로드, 마스킹 누락을 수정한다.
7. 조치 근거와 검토자를 남긴 뒤 경보를 닫는다.

GitHub 문서에 따르면 로그가 삭제된 뒤에도 경보는 남는다.[1] 또한 비밀을 저장소에서 제거했다고 경보가 자동으로 닫히는 것은 아니며 검토자가 직접 종료해야 한다.[3] 경보 종료는 비밀 폐기, 사용처 전환, 활동 검토, 원인 수정이 끝났다는 운영 판정이어야 한다.

### 장기적으로는 로그에 비밀이 필요 없는 구조로 바꾼다

마스킹 규칙을 늘리는 것만으로는 충분하지 않다. 장기 자격 증명을 저장소 secret에 넣고 여러 작업에 전달하는 구조를 줄인다. 클라우드 공급자가 지원한다면 GitHub Actions OIDC로 작업마다 짧은 수명의 역할 자격 증명을 발급하고, 대상 저장소·브랜치·환경에 조건을 건다. `GITHUB_TOKEN` 권한은 워크플로 수준에서 필요한 읽기·쓰기 범위만 명시한다.

셸 디버그 모드, 환경 전체 출력, 예외 객체와 HTTP 헤더 로깅을 기본 금지하고 보안 검토 대상으로 둔다. 서드파티 액션은 커밋 SHA에 고정하고 입력·출력과 로그 동작을 검토한다. 비밀이 필요한 단계와 일반 빌드 단계를 분리해 비신뢰 풀 리퀘스트 코드가 비밀 컨텍스트에 들어오지 않도록 한다.

secret scanning의 한계도 보완한다. 공급자 패턴이 없는 사내 비밀은 현재 Actions 로그 미리보기에서 custom pattern으로 탐지되지 않는다.[1] 따라서 생성 단계에서 짧은 수명·최소 권한을 강제하고, 공급자 측 사용 이상 탐지, 로그 수집기 필터, 워크플로 정적 검사와 코드 리뷰를 결합한다.

## 완료 기준은 탐지 기능이 아니라 대응 루프다

도입 완료를 “토글을 켰다”로 정의하면 공개 미리보기의 공백이 그대로 남는다. 다음 조건을 함께 확인한다.

- 적용 대상 엔터프라이즈·저장소와 예외 목록이 확정됐다.
- 공개 미리보기이며 GA가 아니라는 상태와 확인 날짜가 문서화됐다.
- 백필 없음, 미지원 패턴, 마스킹 값 제외, 무알림 제한이 위험 등록부에 반영됐다.[1]
- 경보 목록을 직접 확인하는 담당자·주기·실패 경보가 있다.
- 실제 자격 증명 없이 수행할 안전 검증안과 증거 필드가 정해졌다.
- 경보가 비밀 폐기·회전, 사용 로그 검토, 원인 수정, 종료 검토로 이어진다.
- 장기 비밀과 과도한 `GITHUB_TOKEN` 권한을 줄이는 개선 항목이 추적된다.

Actions 로그 secret scanning은 이미 새어 나온 비밀을 찾는 유용한 추가 센서다. 그러나 센서가 보지 못하는 영역과 알림 공백을 운영자가 메우지 않으면 경보는 목록에 머물 뿐이다. 마스킹으로 노출을 줄이고, 최소 권한과 짧은 수명으로 피해 반경을 줄이며, 탐지 후에는 반드시 폐기와 회전까지 이어가야 한다.
