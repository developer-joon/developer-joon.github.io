2026년 11월 18일 Ruby 보안팀은 정규식 엔진과 문자열 대소문자 변환에서 발견된 취약점 7건을 한꺼번에 공개했다. 영향 버전은 Ruby 3.3.13 이하, 3.4.0~3.4.12, 4.0.0~4.0.9이며 수정 버전은 3.3.14, 3.4.13, 4.0.10이다. Ruby 3.2 이하는 지원 종료 상태라 이번 수정을 받지 못한다.[1]

일곱 문제는 힙 버퍼 오버플로, double free, 정수 오버플로, 범위 밖 읽기처럼 형태가 다르다. 일부는 공격자가 통제하는 정규식 패턴을 컴파일하거나 문자열 대소문자를 변환하는 경로에서 원격 코드 실행 가능성이 있고, Ruby 팀은 일부 시나리오에서 이를 보이는 PoC를 인지했다고 밝혔다.[1] 이 말은 모든 Ruby 애플리케이션이 곧바로 같은 방식으로 공격된다는 뜻이 아니다. 입력이 해당 연산에 도달하는지와 실제 런타임이 취약한지가 함께 성립해야 한다.

GitLab은 이 차이를 운영 문제로 구체화한다. 11월 20일 공개된 19.6.1, 19.5.8, 19.4.10은 공식 Linux 패키지와 컨테이너 이미지에 수정된 Ruby를 포함한다. 자체 컴파일 GitLab은 애플리케이션 패치만 받아서는 안 되고, GitLab을 실행하는 Ruby를 3.3.14 또는 3.4.13 이상 같은 수정 릴리스로 다시 빌드해야 한다.[2] 즉 “OS Ruby를 업데이트했다”와 “GitLab 프로세스가 수정 Ruby로 실행된다” 사이에는 검증해야 할 전파 경로가 있다.

## 1. 일곱 취약점을 입력 경계별로 읽는다

Ruby 공지는 문자열 대소문자 변환과 정규식 처리라는 두 축을 제시한다. 정규식 쪽에서도 공격자가 패턴 자체를 통제해야 하는 문제, 만들어진 정규식의 문자열 변환에서 발생하는 문제, 공격자가 만든 문자열이 대소문자 무시 역참조 매칭에 들어가는 문제는 도달 조건이 다르다.[1]

따라서 자산 우선순위를 “Ruby 사용 여부”만으로 정하지 않는다. 다음 질문으로 입력 경계를 분해한다.

- 사용자나 외부 시스템이 정규식 **패턴**을 만들 수 있는 기능이 있는가?
- 비신뢰 문자열에 대소문자 변환이나 case-insensitive 매칭을 수행하는가?
- 해당 기능이 인증 전 인터넷 경로, 인증 사용자 경로, 비동기 작업 중 어디에 있는가?
- 요청 크기·실행 시간·작업 큐·프로세스 권한 같은 보조 통제가 있는가?
- 실제 요청을 처리하는 Ruby 런타임은 무엇이며 수정 릴리스인가?

도달 경로를 찾기 위해 취약 입력이나 공개 PoC를 운영 환경에 넣지 않는다. 라우트·코드 호출 관계·기능 소유자·기존 정상 테스트를 사용해 정적·구조적으로 확인한다. 공급자가 PoC 존재를 언급한 것은 긴급도를 높이는 근거지만, 독자의 서비스에서 재현 실험을 요구하는 근거는 아니다.

또한 일곱 GHSA 중 하나만 CVE-2026-132825로 GitLab 공지에 직접 연결됐다고 해서 나머지를 무시하면 안 된다. GitLab은 해당 패치 릴리스에 Ruby 공지의 다른 취약점 수정도 포함된다고 설명한다.[2] 각 애플리케이션은 업스트림 공지의 전체 영향 범위와 자신의 번들 방식을 함께 봐야 한다.

## 2. 런타임 인벤토리는 설치·아티팩트·프로세스 세 층이다

서버에서 `ruby --version`을 한 번 실행하면 셸의 `PATH`가 가리키는 Ruby만 보인다. GitLab Omnibus 패키지, 컨테이너 이미지, rbenv·RVM·asdf, 애플리케이션 전용 경로, 정적 빌드에는 서로 다른 Ruby가 있을 수 있다. 현재 프로세스는 파일 시스템에서 방금 갱신된 바이너리가 아니라 이전에 로드한 런타임을 계속 사용할 수도 있다.

인벤토리는 다음 세 층을 연결한다.

| 층 | 확인 대상 | 최소 증거 |
|---|---|---|
| 설치 | OS 패키지, rbenv/RVM/asdf, 자체 빌드 | 공급자·버전·설치 경로 |
| 아티팩트 | Omnibus, 컨테이너, VM 이미지, 배포 번들 | 패키지 릴리스·이미지 다이제스트·빌드 기록 |
| 실행 | web, worker, job, console 프로세스 | PID·실행 경로·시작 시각·프로세스 내부 버전 |

SBOM도 한 층의 증거다. 소스 의존성 SBOM에는 런타임이 없을 수 있고, 이미지 SBOM은 현재 배포된 다이제스트를 증명하지 않는다. 반대로 현재 프로세스의 버전만 보면 다음 오토스케일 때 사용될 오래된 골든 이미지가 남을 수 있다. 세 층을 같은 자산 ID로 연결해야 한다.

수집 과정에서는 프로세스 전체 명령줄과 환경 변수를 중앙 로그에 올리지 않는다. 자격 증명, 토큰, 데이터베이스 URL이 들어 있을 수 있기 때문이다. 실행 파일 경로, PID, 시작 시각, 버전처럼 필요한 필드만 허용 목록으로 수집하고 결과 파일 권한을 제한한다.

승인된 GitLab 관리자가 애플리케이션 내부 런타임을 확인할 때는 해당 설치 방식의 공식 관리 명령을 사용한다. 다음은 일반 Ruby 프로세스가 자신의 버전만 출력하는 최소 예시이며 운영 GitLab 명령을 대신하지 않는다.

```bash
#!/usr/bin/env bash
set -euo pipefail
ruby -e 'puts RUBY_DESCRIPTION'
```

이 결과는 그 명령을 실행한 런타임만 증명한다. 웹과 백그라운드 작업 프로세스가 같은 바이너리를 쓰는지는 서비스별로 따로 확인한다. 이 글에서는 실제 환경에 명령을 실행하지 않았으므로 특정 배포가 수정됐다고 주장하지 않는다.

## 3. GitLab 설치 방식마다 수정 전파 경로가 다르다

GitLab 공식 공지는 Community Edition과 Enterprise Edition의 19.6.1, 19.5.8, 19.4.10에 수정된 번들 Ruby가 들어 있다고 설명한다. 영향 범위는 19.4.10 미만의 모든 버전, 19.5 계열의 19.5.8 미만, 19.6 계열의 19.6.1 미만이다.[2] GitLab.com과 GitLab Dedicated는 이미 수정됐다고 공지했으므로 고객이 자체 인프라 패치를 수행하는 self-managed 범위와 구분한다.

공식 Linux 패키지는 GitLab 패키지 자체를 목표 패치 릴리스로 올려야 한다. 호스트의 `/usr/bin/ruby`만 바꿔도 Omnibus 내부 Ruby에는 전파되지 않을 수 있다. 공식 컨테이너는 수정 태그를 받는 데서 끝내지 말고 immutable digest로 고정하고, 각 노드의 실행 Pod가 새 다이제스트로 교체됐는지 확인한다. mutable tag를 재사용하면 배포 증거가 약해진다.

자체 컴파일 설치는 더 명시적이다. GitLab 공지는 GitLab을 실행하는 Ruby를 수정된 3.3.14 또는 3.4.13 이상으로 다시 빌드하라고 요구한다.[2] 시스템 라이브러리와 Ruby 빌드 캐시, 배포 사용자 환경, 서비스 단위 파일이 어느 경로를 참조하는지 확인한다. 새 Ruby를 설치했어도 서비스가 이전 경로를 사용하면 수정은 전파되지 않는다.

GitLab이 11월 25일 추가 백포트를 제공했다면 조직이 실제 운영하는 지원 브랜치의 최신 패치 공지를 다시 확인해야 한다. 이 글에 적힌 최초 세 릴리스만 고정 목표로 삼지 말고 발행 후 나온 더 최신 보안 패치를 선택한다. 단, 새 버전이 있다는 이유로 본문에 없는 영향 범위를 추정해서는 안 된다. 변경 시점의 개별 GitLab 릴리스 공지와 업그레이드 문서를 근거로 목표를 확정한다.

## 4. 재빌드와 재배포를 프로세스까지 검증한다

안전한 변경은 현재 상태의 증거와 롤백 기준부터 만든다. 데이터베이스 백업, 저장소·객체 저장소 정합성, 구성 백업, 복원 담당자를 확인한다. GitLab 공지는 해당 세 릴리스에 새 마이그레이션이 없고 다중 노드에서 무중단 업그레이드가 가능할 수 있다고 설명하지만, 기본 Omnibus 업그레이드는 중지·재구성·시작을 수행할 수 있다고 주의한다.[2] 조직의 토폴로지와 절차를 그대로 대입하지 않는다.

컨테이너라면 새 이미지를 CI에서 다시 빌드해도 캐시가 오래된 base image를 고정할 수 있다. 빌드 로그의 base digest, 최종 digest, SBOM의 Ruby 버전, 서명·출처를 함께 남긴다. 이후 선언된 digest와 실행 중인 digest를 대조한다. 패키지 설치라면 패키지 버전과 번들 Ruby 경로를 확인하고 관련 서비스가 패치 이후 시작됐는지 본다.

검증표는 최소 다음을 포함한다.

1. 모든 web·API·background worker·tooling 프로세스가 목표 런타임으로 재시작됐다.
2. 실행 중인 각 프로세스의 시작 시각이 패치 배포 이후다.
3. 새 오토스케일 인스턴스와 재해복구 환경도 수정 이미지에서 시작한다.
4. 로그인, 프로젝트 조회, push/pull, CI 작업 예약, 백그라운드 큐 같은 핵심 정상 경로가 통과한다.
5. 오류율, worker crash, 큐 지연, 메모리 사용량이 기준선을 벗어나지 않는다.
6. 롤백할 경우 취약 런타임으로 되돌아가지 않도록 보안 승인 조건이 있다.

취약 입력으로 크래시나 코드 실행을 재현하지 않는다. 기존 정상 회귀 테스트와 프로세스 내부 버전 증명으로 패치 전파를 검증한다. 보안 수정의 목적은 위험한 동작을 반복해 보는 것이 아니라 취약 코드가 더는 실행 경로에 없다는 증거를 만드는 것이다.

## 5. 패치 전 노출과 이상 징후를 별도 평가한다

Ruby 공지는 일부 문제의 RCE PoC를 알고 있다고 했지만 실제 악용 캠페인을 확인했다고 말하지 않는다.[1] 그러므로 “실제 악용 중”으로 부풀리지 않는다. 동시에 외부 입력이 도달하는 인터넷 서비스와 CI·협업 플랫폼은 패치 전 기간의 이상을 검토할 가치가 있다.

관찰 대상은 Ruby 프로세스의 segmentation fault, abort, 비정상 재시작, core dump, 요청 오류 급증, background worker의 반복 실패다. GitLab에서는 웹·Sidekiq·Gitaly 등 역할을 섞지 말고 Ruby를 사용하는 프로세스와 그렇지 않은 구성요소를 구분한다. 같은 시각의 WAF, 리버스 프록시, 애플리케이션 상관 ID, 컨테이너 이벤트를 연결한다.

크래시 하나를 공격으로 확정하지 않는다. 배포 오류, 메모리 부족, 확장 모듈 결함 등 대안 원인을 함께 조사한다. 반대로 로그가 없다는 이유로 침해 없음을 단정하지 않는다. 보존 기간, core dump 비활성화, 컨테이너 교체로 가시성이 사라졌을 수 있다.

의심 징후가 있으면 노드를 트래픽에서 빼고 증거를 보존한다. 즉시 이미지나 로그를 삭제하지 않는다. 애플리케이션 비밀, CI runner token, 저장소 접근 키의 노출 가능성은 프로세스 권한과 확인된 행위를 기준으로 평가한다. 무조건 전체 비밀을 동시에 회전해 가용성을 해치기보다, 격리·신뢰할 수 있는 재구축·우선순위 회전을 사고 대응 계획으로 묶는다.

## 6. 완료 기준은 “설치됨”이 아니라 “전파됨”이다

이번 대응의 종료 조건은 다음과 같다.

- Ruby 3.3.13 이하, 3.4.0~3.4.12, 4.0.0~4.0.9가 남아 있는 자산을 찾았거나 정당한 예외로 격리했다.
- 지원 종료된 Ruby 3.2 이하를 지원 브랜치로 이동하거나 서비스를 교체할 계획이 승인됐다.
- GitLab 설치 방식별 공식 패치 릴리스 또는 더 최신 지원 패치를 적용했다.
- 시스템 Ruby가 아니라 애플리케이션이 실제 로드한 Ruby 버전을 증명했다.
- 컨테이너·골든 이미지·오토스케일·재해복구 아티팩트도 함께 갱신됐다.
- 모든 관련 프로세스가 새 아티팩트에서 다시 시작됐고 정상 기능을 검증했다.
- 패치 전 노출 기간과 이상 징후 검토 결과, 증거 공백을 기록했다.

런타임 취약점은 패키지 관리자의 초록색 체크 하나로 끝나지 않는다. 소스, 빌드, 이미지, 배포, 프로세스가 하나의 계보를 이룬다. 마지막 실행 프로세스까지 수정 버전이 도달했다는 증거가 있을 때만 “Ruby 패치가 GitLab에 적용됐다”고 말할 수 있다.
