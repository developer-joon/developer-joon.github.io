CISA가 취약점을 Known Exploited Vulnerabilities(KEV) 카탈로그에 넣었다면 대응 질문은 “언제 패치할까?”에서 끝나지 않는다. 취약 버전이 노출됐던 기간에 침해가 일어났는지, 패치 전에 어떤 증거를 보존할지, 이상이 확인되면 무엇을 다시 신뢰할지까지 같은 작업 계획에 들어가야 한다.

CISA는 2026년 11월 25일 CVE-2026-103406을 KEV에 추가했다. 목록의 제품 표기는 HPE Juniper Session Smart Conductor and Session Smart Router이며, 추가 근거는 실제 악용 증거다.[1] 하지만 세부 영향 조건은 이 집계 목록만으로 결정하면 안 된다. CVE의 Juniper CNA 레코드는 취약 구성요소를 Session Smart **Conductor**의 AutomatedProvisioner로 특정하고, 원격 공격자가 키 관리 과정에서 명령을 root 권한으로 실행할 수 있는 OS command injection 문제라고 설명한다.[2]

Juniper bulletin JSA112183은 Session Smart Router와 Conductor의 여러 취약점을 한꺼번에 다룬다.[3] 따라서 bulletin 전체의 제품 범위와 CVE-2026-103406 하나의 제품 범위를 섞지 않는 것이 첫 번째 원칙이다. 이 글은 공격에 쓰인 식별자 형식이나 명령 문자열을 재현하지 않고, Conductor 관리면의 노출 확인·업그레이드·증거 보존·복구 판정에 집중한다.

## 1. KEV와 개별 advisory가 답하는 질문은 다르다

KEV는 “실제 악용 증거가 있어 우선 대응해야 하는가?”에 답한다. CISA의 11월 25일 공지는 CVE-2026-103406을 실제 악용 취약점 목록에 추가했다고 확인한다.[1] 그러나 공격 전제조건, 영향 버전, 수정 릴리스, 제품 역할은 Juniper의 개별 advisory와 CNA 레코드에서 확인해야 한다.

Juniper CNA 레코드가 제시하는 CVE-2026-103406의 영향 범위는 다음과 같다.[2]

- 7.0.5 미만
- 7.1.0 이상 7.1.7 미만
- 7.2.0 이상 7.2.3 미만

수정 릴리스는 각 계열의 7.0.5, 7.1.7, 7.2.3 이상이다. 레코드의 기본 상태는 명시된 범위 밖을 unaffected로 두지만, 이것을 지원 종료 제품의 안전 보증으로 확대하지 않는다. EOL 장비는 현재 지원되는 업그레이드 경로와 별도 위험 결정을 공급자에게 확인한다.

제품명 혼선도 주의한다. CISA 항목과 다중 취약점 bulletin은 Router를 함께 언급하지만, CVE 레코드의 해당 명령 주입 취약점은 Session Smart Conductor로 특정된다.[1][2] Router도 JSA112183의 다른 취약점과 패치 대상일 수 있으므로 전체 bulletin을 검토해야 하지만, CVE-2026-103406의 세부 조건을 Router에 임의로 복사해서는 안 된다.

## 2. Router와 Conductor를 역할 중심으로 인벤토리한다

자산 검색은 벤더 문자열만으로 하면 누락되기 쉽다. 인수 전 제품명, 클라우드 관리 명칭, 어플라이언스 이미지, 가상 머신 태그가 서로 다를 수 있다. CVE, 정확한 역할, 관리 관계를 중심으로 찾는다.

| 항목 | 기록할 값 | 목적 |
|---|---|---|
| 자산 역할 | Conductor, Router, 관리 노드 | CVE와 bulletin 범위 구분 |
| 버전 | 전체 릴리스·빌드 문자열 | 영향·수정 범위 대조 |
| 관리 관계 | Conductor가 관리하는 Router 집합 | 변경 순서와 반경 파악 |
| 관리면 노출 | 인터넷, VPN, 전용망, 내부 | 우선순위와 조사 기간 설정 |
| 주소·DNS | 관리 인터페이스의 승인된 식별자 | 중복·유령 자산 제거 |
| HA 상태 | 노드·클러스터·리더 역할 | 증거 보존과 업그레이드 계획 |
| 로그 목적지 | 로컬·SIEM·보존 기간 | 포렌식 가시성 판단 |
| 지원 상태 | 지원·EOL·계약 | 목표 릴리스 결정 |
| 소유자 | 네트워크·보안·서비스 팀 | 승인과 복구 책임 지정 |

외부 공격 표면 관리 도구의 결과는 후보 목록으로만 쓴다. NAT, 프록시, ACL, VPN, 방화벽 정책과 실제 리스너를 대조한다. “인터넷 검색에 안 보인다”는 결과가 관리면 비노출을 증명하지 않는다. 파트너망이나 침해된 내부 호스트에서 도달할 수 있는 경로도 별도 위험이다.

Conductor와 Router의 버전 호환성, HA 업그레이드 순서, 구성 백업·복원 방식은 현재 지원 문서를 따른다. 운영자가 익숙한 일반 Linux 명령을 어플라이언스에서 임의 실행하면 지원 상태나 증거를 훼손할 수 있다. 공급자 지원 절차와 조직의 변경 승인 범위 안에서 읽기 전용 정보를 수집한다.

## 3. 패치 전에 노출 기간과 증거 보존선을 확정한다

실제 악용이 확인된 취약점은 재부팅과 업그레이드가 중요한 흔적을 덮어쓸 수 있다. 그렇다고 패치를 오래 미뤄서는 안 된다. 짧은 사전 보존 단계와 긴급 노출 축소를 병렬로 진행한다.

먼저 관리 인터페이스를 승인된 관리망·VPN·점프 호스트로 제한한다. 인터넷 ACL을 제거하거나 방화벽 허용 목록을 좁히고, 변경 전후 정책과 시각을 남긴다. 정상 라우팅 데이터면을 불필요하게 끊지 않도록 관리면과 데이터면을 구분한다. 고가용성 쌍을 동시에 격리하거나 재시작하지 않는다.

증거 보존 범위는 최소 다음을 포함한다.

- 현재 버전·빌드, uptime, HA 역할, 구성 체크섬
- 관리자·서비스 계정과 최근 인증·권한 변경 이력
- Conductor 관리·키 관리·프로비저닝 관련 감사 및 시스템 로그
- 비정상 프로세스, 서비스, 예약 작업, 시작 항목의 메타데이터
- 관리면의 수신 연결과 장비에서 나간 예기치 않은 외부 연결
- Router 등록·해제·재등록, 정책·구성 배포 이력
- 중앙 SIEM, 방화벽, DNS, 프록시의 동일 시간대 기록

명령줄 전체, 환경 변수, 키 자료를 일반 티켓에 복사하지 않는다. 키 관리 시스템인 만큼 비밀이 로그나 프로세스 인자에 섞일 가능성을 전제로 필드를 최소화한다. 원본은 접근 통제된 증거 저장소에 보관하고 해시, 수집 시각, 수집자, 장비 시계를 기록한다.

조사 시작 시점은 취약 버전이 배포되고 관리면이 잠재적으로 도달 가능해진 시각이다. 그것을 알 수 없다면 로그 보존이 허용하는 가장 이른 시각까지 넓히고 “이전 기간 판정 불가”를 명시한다. KEV 추가일인 11월 25일만 조사 시작점으로 삼으면 그 전에 발생한 활동을 놓친다.

## 4. 패치는 지원 릴리스와 관리면 축소를 함께 적용한다

CVE 레코드 기준 목표는 해당 브랜치의 7.0.5, 7.1.7, 7.2.3 이상이다.[2] 실제 변경일에는 JSA112183과 최신 릴리스 노트를 다시 확인해 더 최신 지원 패치가 있는지 확인한다. 숫자가 높다는 이유만으로 다른 브랜치의 호환성을 추정하지 않는다.

변경 전에는 구성 백업의 생성뿐 아니라 복원 절차와 암호화 키 접근을 확인한다. HA 환경에서는 한 노드씩 업그레이드하고 리더 전환, 세션 유지, 구성 동기화, Router 연결 상태의 합격 기준을 정의한다. EOL 계열은 단순 예외 처리하지 말고 지원 릴리스로 마이그레이션하거나 관리면을 강하게 격리한 단기 계획과 폐기 일정을 승인받는다.

업그레이드 후 확인할 항목은 다음과 같다.

1. 모든 Conductor 노드가 목표 버전 이상이며 이전 노드가 클러스터나 로드밸런서에 남지 않았다.
2. 실행 중인 프로세스와 서비스 시작 시각이 업그레이드 이후다.
3. Router가 정상 연결되고 정책·라우팅·세션 상태가 조직의 기준 범위다.
4. 관리자 로그인과 승인된 프로비저닝 흐름이 정상이다.
5. 관리 인터페이스는 지정 관리망에서만 도달 가능하다.
6. 로그가 중앙 저장소로 계속 전달되고 장비 시간이 동기화된다.
7. 재해복구 이미지와 신규 설치 템플릿도 수정 릴리스로 갱신됐다.

정상 기능 확인에 공격용 식별자나 명령 주입 문자열을 사용하지 않는다. 승인된 장비 등록, 읽기 전용 상태 조회, 평범한 구성 배포처럼 기존 운영 테스트로 검증한다. 이 글에서는 실제 장비에 검증을 실행하지 않았으므로 위 항목은 실행 결과가 아니라 제안된 수용 기준이다.

## 5. 포렌식 선별은 계정·구성·프로세스·네트워크를 연결한다

CVE-2026-103406은 원격 공격자가 Conductor에서 root 명령 실행에 이를 수 있는 문제로 설명된다.[2] 따라서 웹 접근 로그만 보는 것으로 충분하지 않다. 성공했을 경우 시스템·구성·연결 흔적이 어느 범위에 남을지 권한 기준으로 조사한다.

**계정과 인증**에서는 새 관리자, 역할 변경, 키·인증서 교체, 실패 후 성공한 비정상 로그인, 휴면 계정 사용을 본다. **구성과 관리 관계**에서는 승인되지 않은 Router 등록, 정책 변경, 관리 주소·DNS·NTP·로그 목적지 변경을 확인한다. **호스트 동작**에서는 낯선 root 프로세스, 서비스·예약 작업·시작 항목, 시스템 바이너리와 패키지 변화를 살핀다. **네트워크**에서는 Conductor가 평소 접속하지 않던 외부 주소로 연결했는지, 관리면에 비정상 출발지가 집중됐는지 확인한다.

각 신호는 시간축과 변경 기록에 맞춘다. 업그레이드 작업이 프로세스·파일·연결 변화를 만들 수 있고, 정상 Router 온보딩도 키 관리 이벤트를 발생시킨다. 승인 티켓, 운영자 세션, 자동화 실행 ID와 비교해 오탐을 줄인다.

Juniper가 제공하는 IoC가 있다면 알려진 활동을 찾는 하나의 필터로 사용한다. IoC 일치가 없다는 이유로 침해를 배제하지 않는다. 공급자에게 보고된 캠페인의 흔적과 모든 가능한 공격자의 흔적은 같지 않다. 로그가 순환됐거나 장비가 이미 재부팅됐다면 판정 신뢰도가 낮아진 사실을 기록한다.

의심 노드는 관리면과 외부 통신에서 격리하되, 라우팅 중단의 안전 영향을 네트워크 팀과 조정한다. 제자리에서 파일을 삭제하거나 알 수 없는 프로세스를 먼저 종료하면 증거가 사라질 수 있다. 공급자 지원과 사고 대응팀이 메모리·디스크·지원 번들 수집의 순서를 정하도록 한다.

## 6. 침해 가능성이 있으면 복구 신뢰점을 새로 만든다

root 수준 실행 가능성이 확인되거나 강하게 의심되면 단순 인플레이스 패치만으로 장비를 다시 신뢰하기 어렵다. 신뢰할 수 있는 공급자 이미지로 Conductor를 재구축하고, 검토한 구성만 복원한다. 침해 추정 시점 이후의 백업은 악성 계정이나 설정을 포함할 수 있으므로 diff와 변경 이력을 확인한다.

비밀 회전 범위는 Conductor가 접근할 수 있었던 것에서 시작한다. 관리자 자격 증명, Router와의 신뢰 자료, API 토큰, 인증서 개인키, 백업 저장소·SIEM·IdP 연동 비밀을 목록화한다. 모두 무차별 동시 회전하기보다 공격자가 실제로 접근 가능했던 권한, 의심 행위, 서비스 의존성을 기준으로 순서를 정한다. 단, 새 비밀을 의심 장비에 먼저 배포해서는 안 된다. 깨끗한 환경 구축과 격리 뒤에 회전한다.

Router와 데이터면의 영향도 증거에 따라 확대한다. Conductor 침해 가능성만으로 모든 Router가 변조됐다고 단정하지 않지만, 중앙에서 배포할 수 있었던 구성과 관리 작업을 검토한다. 승인된 기준 구성과 현재 상태를 비교하고, 의심 변경이 있으면 영향 Router를 단계적으로 재검증한다.

복구 뒤에는 관리면을 인터넷에 되돌리지 않는 것을 기본으로 검토한다. 전용 관리망, MFA가 적용된 점프 호스트, 소스 허용 목록, 중앙 감사 로그, egress 제한을 지속 통제로 둔다. 긴급 ACL을 임시 조치로만 남겼다가 며칠 뒤 자동 만료시키지 말고 영구 설계로 전환한다.

## 7. 종료 조건은 패치와 침해 판정을 분리한다

**취약 상태 제거 완료**는 모든 해당 Conductor가 지원되는 수정 릴리스 이상이고, 이전 노드·DR 이미지·설치 템플릿이 제거됐으며, 관리면 접근이 제한되고, 정상 라우팅과 관리 기능이 검증됐다는 뜻이다.

**침해 평가 완료**는 취약 버전의 노출 기간을 정했고, 계정·구성·프로세스·네트워크 증거를 검토했으며, 의심 사항과 가시성 공백을 처리했다는 뜻이다. 확인 가능한 로그가 없으면 “침해 없음”이 아니라 “판정 제한”이다. 침해가 확인되거나 배제할 수 없다면 재구축, 비밀 회전, Router 구성 검증, 강화된 모니터링까지 복구 조건에 포함한다.

KEV는 패치 우선순위를 알려 주지만 조직의 침해 여부를 알려 주지는 않는다. 개별 Juniper advisory와 CVE 레코드로 정확한 제품·버전·구성요소를 판정하고, CISA의 실제 악용 신호를 근거로 포렌식 선별을 같은 변경 창에 넣어야 한다. 그래야 “업데이트됨”과 “다시 신뢰할 수 있음” 사이의 빈칸을 줄일 수 있다.
