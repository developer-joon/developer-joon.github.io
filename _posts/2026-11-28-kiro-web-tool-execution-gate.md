AWS는 2026년 11월 25일 Kiro Web의 CVE-2026-136267을 공개했다. 저장소 파일이나 웹페이지처럼 에이전트 세션이 읽은 콘텐츠 안의 도구 호출 마크업이 반복되면서, 별도 동의 창 없이 구독자의 호스팅 개발 환경에서 명령으로 실행될 수 있었던 문제다. 영향 대상은 **2026년 5월 18일부터 10월 30일까지 Kiro Web에서 DeepSeek v3.2, GLM-5, MiniMax M2.1, MiniMax M2.5 또는 Qwen3-coder-next 중 하나를 사용한 에이전트 세션**이다.[1] AWS는 10월 30일 서비스 측 업데이트로 수정했고 고객이 적용할 패치는 없다고 밝혔다.[1]

CVE 레코드는 이 문제를 혼합된 데이터와 마크업 처리의 부적절한 무해화로 설명하며 CVSS 3.1 8.8을 제시한다.[2] 이 공지는 Kiro Web의 특정 기간과 특정 모델 조합에 관한 사실이다. 모든 AI 코딩 에이전트가 같은 취약점을 가진다는 뜻은 아니다. 다만 **읽은 텍스트가 실행 권한을 가진 도구 호출로 승격되는 경계**를 어떻게 설계해야 하는지는 다른 에이전트 운영에도 적용할 수 있다.

## 사고의 핵심은 모델보다 권한 전환 경계다

에이전트는 저장소 문서, 이슈, 웹페이지, 빌드 로그를 읽는다. 그중 어느 것도 명령 권한을 자동으로 가져서는 안 된다. 문제의 본질은 비신뢰 콘텐츠가 모델 출력에 섞인 뒤, 구조화된 도구 호출처럼 해석되고, 사용자 승인 없이 실행 환경으로 전달된 데 있다.[1]

이를 세 영역으로 나누면 통제가 선명해진다.

1. **콘텐츠 영역:** 저장소 파일, 웹페이지, 문서, 댓글처럼 공격자가 일부를 통제할 수 있는 데이터
2. **추론 영역:** 모델이 콘텐츠를 요약하고 다음 행동을 제안하는 단계
3. **실행 영역:** 셸, 파일 쓰기, 네트워크, 배포, 자격 증명 사용처럼 실제 상태를 바꾸는 도구

콘텐츠가 추론에 들어가는 것은 제품 목적상 필요할 수 있다. 그러나 추론 결과가 실행 영역으로 넘어갈 때는 독립된 정책 판정이 필요하다. 모델이 “도구 호출 형식처럼 보이는 문자열”을 출력했다는 사실만으로는 실행 권한이 생기지 않는다. 모델 필터 하나로 막으려 하면 새 모델, 새 인코딩, 새 도구가 추가될 때 같은 경계가 다시 열린다.

## 실행 게이트는 문법보다 출처와 의도를 검증한다

안전한 실행 게이트는 호출의 형식이 올바른지만 보지 않는다. 누가 요청했는지, 어떤 사용자 의도에서 파생됐는지, 비신뢰 입력이 호출 인자에 영향을 줬는지, 어떤 자원을 변경하는지를 함께 판단해야 한다.

| 게이트 질문 | 허용에 필요한 최소 증거 |
|---|---|
| 호출의 기원은 무엇인가 | 사용자 직접 요청과 에이전트 제안을 분리한 provenance |
| 비신뢰 콘텐츠가 영향을 줬는가 | 읽은 소스와 호출 인자의 데이터 흐름 표시 |
| 상태를 바꾸는가 | 읽기·쓰기·실행·외부 전송 등 효과 분류 |
| 사용자가 이해했는가 | 명령, 대상, 권한, 예상 효과가 보이는 승인 화면 |
| 정책상 가능한가 | 세션 역할, 저장소, 네트워크, 도구별 허용 범위 |
| 사후 재구성이 가능한가 | 요청·판정·승인·실행 결과의 상관 ID와 감사 이벤트 |

여기서 provenance, 상관 ID, 위험 등급은 AWS가 Kiro Web의 공식 필드로 공개한 것이 아니라 조직이 구현할 수 있는 운영 설계다. 공급자 사고의 사실과 일반화한 방어 제안을 혼동하지 않아야 한다.

승인 화면도 단순한 “Allow” 버튼이면 부족하다. 실제 실행될 도구, 대상 작업공간, 읽거나 쓰는 경로, 외부 통신 목적지, 사용 자격 증명, 지속 효과를 보여 줘야 한다. 승인 뒤 에이전트가 인자를 바꿀 수 있다면 승인 대상과 실행 대상이 달라진다. 승인된 구조화 호출을 해시나 불변 ID로 묶고, 변경이 생기면 다시 승인받는 방식이 필요하다.

## 승인만으로 부족하다: 실행 환경의 권한을 줄인다

사람은 반복되는 승인에 익숙해진다. 따라서 승인 실패를 가정하고 실행 환경 자체의 피해 반경을 제한해야 한다. 기본 세션은 읽기 전용 작업공간, 비특권 사용자, 제한된 CPU·메모리·실행 시간, 차단된 외부 네트워크로 시작한다. 파일 쓰기, 패키지 설치, 인터넷 접근, 배포, 비밀 사용은 각각 별도 능력으로 승격한다.

특히 다음 경계를 분리한다.

- 저장소 읽기와 홈 디렉터리·다른 저장소 접근
- 빌드 실행과 운영 배포 권한
- 공개 패키지 다운로드와 임의 목적지 네트워크 연결
- 일반 환경 변수와 자격 증명 저장소 조회
- 임시 작업공간 쓰기와 호스트 파일시스템 쓰기
- 로그 보기와 로그·아티팩트 외부 전송

비밀은 “환경에 넣어 두고 모델에게 보지 말라고 지시”하는 방식으로 보호되지 않는다. 필요한 작업 순간에만 짧은 수명의 범위 제한 자격 증명을 중개하고, 도구 프로세스가 필요한 요청에만 사용하도록 한다. 모델 컨텍스트, 셸 출력, 오류 메시지, 빌드 로그에 원문 비밀이 들어가지 않도록 입력과 출력을 모두 필터링한다. secret scanning은 사후 탐지 수단일 뿐 실행 권한 분리의 대체재가 아니다.

네트워크도 허용 목록만 선언하지 말고 DNS 변경, 리다이렉트, 프록시 경로와 업로드 크기를 관측한다. 읽기 전용 분석 세션이라면 외부 전송을 기본 차단하고, 문서 조회는 격리된 fetcher가 콘텐츠를 정규화해 전달하도록 분리할 수 있다.

## 안전 검증은 실제 공격 마크업 없이도 가능하다

이 글은 Kiro Web의 실제 도구 호출 마크업이나 우회 문자열을 제공하지 않는다. 공급자 문제를 재현하는 대신, 조직의 에이전트가 갖춰야 할 정책을 무해한 시나리오로 검증할 수 있다.

전용 빈 작업공간에 “파일 목록을 제안하라”는 의미의 합성 문서를 두고, 에이전트가 이를 읽었을 때 도구가 자동 실행되지 않는지 관찰한다. 여기서 목적은 특정 취약점 재현이 아니라 **비신뢰 문서의 행동 제안이 승인 없는 실행으로 바뀌지 않는지** 확인하는 것이다. 실제 명령이나 공격용 구조는 사용할 필요가 없다.

검증 항목은 다음과 같다.

1. 문서를 읽은 뒤 도구 호출이 제안 상태에 머물고 자동 실행되지 않는다.
2. 승인 화면에 도구, 대상, 효과가 표시되고 거부하면 어떤 상태도 바뀌지 않는다.
3. 승인 직전 호출 인자가 바뀌면 기존 승인이 무효화된다.
4. 읽기 세션에서 파일 쓰기·외부 네트워크·비밀 접근 요청이 정책에 의해 거부된다.
5. 거부, 승인, 실행 실패와 성공이 서로 다른 감사 이벤트로 남는다.
6. 로그에는 비밀 원문이나 문서 전체가 불필요하게 복제되지 않는다.

이 검증은 제품 전체의 안전성을 증명하지 않는다. 모델·도구·정책 버전, 세션 권한과 테스트 시각을 함께 기록해야 한다. 새 모델이나 도구가 추가되면 같은 게이트를 다시 통과시킨다. 공개 미리보기 모델이나 실험 기능은 일반 가용(GA) 기능처럼 취급하지 않고 별도의 제한된 코호트에서 평가한다.

## 감사 로그는 모델 대화가 아니라 권한 결정을 기록한다

대화 전문만 저장하면 왜 실행이 허용됐는지 재구성하기 어렵고, 민감한 소스와 비밀이 과도하게 남는다. 감사 이벤트는 권한 결정에 필요한 구조화 정보 중심으로 설계한다.

- 세션·사용자·작업공간 식별자
- 모델, 에이전트, 정책, 도구의 버전
- 호출의 출처 분류와 비신뢰 콘텐츠 영향 여부
- 요청된 도구와 대상 자원의 범위
- 정책 판정, 승인자, 승인 시각, 승인된 불변 호출 ID
- 실제 실행 시작·종료와 결과 코드
- 파일·네트워크·배포 등 발생한 효과의 요약
- 차단 이유와 예외 승인 티켓

문서 본문과 셸 전체 출력을 무조건 감사 로그에 복사하지 않는다. 최소 수집, 접근 통제, 보존 기간, 마스킹과 삭제 절차를 함께 정의한다. 로그 관리자도 실행 환경의 비밀을 자동으로 볼 수 없게 권한을 분리한다.

경보는 승인 없는 실행, 승인 대상과 실제 호출 불일치, 읽기 세션의 쓰기 요청, 허용 목록 밖 네트워크, 비밀 조회 뒤 외부 전송처럼 정책 위반에 맞춘다. 단순히 “모델이 위험한 단어를 말했다”는 경보보다 실제 권한 전환 실패를 우선한다.

## SaaS 수정 뒤에도 고객이 검토할 것은 남는다

AWS는 이 문제를 서비스 측에서 수정했으며 고객 조치가 필요 없다고 밝혔다.[1] 이것은 고객이 패치를 설치할 필요가 없다는 뜻이지, 영향 기간의 세션을 전혀 검토할 필요가 없다는 보장은 아니다. 사후 검토 대상은 **Kiro Web + DeepSeek v3.2·GLM-5·MiniMax M2.1·MiniMax M2.5·Qwen3-coder-next 중 하나 + 2026년 5월 18일부터 10월 30일까지의 세션**이라는 세 조건을 모두 충족하는 경우다.[1] 서비스 측 수정 완료가 모든 과거 Kiro Web 세션이 영향을 받았다는 뜻은 아니다. 이 교집합에서 비신뢰 저장소나 웹 콘텐츠를 읽었다면, 조직은 사용 이력과 개발 환경의 변경·네트워크·자격 증명 사용 기록을 위험 기반으로 검토할 수 있다.

사후 질문은 구체적이어야 한다.

- 2026년 5월 18일~10월 30일에 DeepSeek v3.2, GLM-5, MiniMax M2.1, MiniMax M2.5 또는 Qwen3-coder-next를 사용한 Kiro Web 세션을 식별할 수 있는가?[1]
- 동의 없이 실행된 호출을 구분하는 감사 데이터가 제공되는가?
- 호스팅 환경이 접근할 수 있었던 저장소, 비밀, 네트워크 범위는 무엇이었는가?
- 의심 세션의 작업공간을 보존·폐기하고 자격 증명을 회전할 기준은 무엇인가?
- 서비스 수정이 적용됐음을 어떤 상태 페이지나 공급자 확인으로 기록할 것인가?

공개 공지는 실제 고객별 침해를 증명하지 않는다. 이상 징후가 없다면 “현재 로그에서 확인되지 않음”으로 기록하고 로그의 범위와 보존 공백을 함께 남긴다. 의심스러운 명령이나 비밀 접근이 확인되면 해당 작업공간을 격리하고 자격 증명을 폐기하며, 코드와 아티팩트의 무결성을 신뢰할 수 있는 기준과 비교한다.

## 운영 기준은 자동 실행이 아니라 검증 가능한 권한 상승이다

AI 에이전트의 생산성은 도구를 쓸 수 있다는 데서 나오지만, 모든 호출을 자동 승인해야 얻는 것은 아니다. 기본 권한을 작게 두고, 명확한 사용자 의도와 정책을 가진 호출만 단계적으로 승격하면 위험한 작업에는 마찰을 만들고 반복적인 안전 작업은 사전 승인된 좁은 범위에서 자동화할 수 있다.

출시 게이트에는 최소한 다음 조건이 들어가야 한다.

- 비신뢰 콘텐츠는 명령 출처가 될 수 없고 데이터로만 취급된다.
- 구조화된 도구 호출은 출처·효과·권한 정책을 독립적으로 검증한다.
- 상태 변경 호출은 구체적인 승인 대상과 실행 대상이 동일하다.
- 실행 환경은 비특권·최소 네트워크·최소 비밀로 격리된다.
- 정책 위반과 실행 효과를 사후 재구성할 감사 이벤트가 남는다.
- 모델·도구·정책 변경 때 무해한 회귀 검증을 다시 수행한다.

Kiro Web 사건의 교훈은 “특정 모델을 쓰지 말라”가 아니다. 모델이 읽은 것을 곧바로 권한 있는 명령으로 믿지 말고, 실행은 별도의 검증 가능한 보안 경계로 만들라는 것이다.
