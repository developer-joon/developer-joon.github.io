# Domestic employer search and benefit-first display

## Goal and approved scope

Make a materially wider **searchable domestic employer directory** while leaving the existing 2,000-entity identity/projection and 128 research-only benefit actions intact. List actual benefit actions, not topic labels or reference-link prose, when attributable evidence exists. Preserve the distinction between a company being searchable, a dated recruitment/workplace observation, a current employer, a current benefit policy, and an approved benefit. Do not imply this is a complete registry of Korean businesses.

The user approved size navigation using large enterprise, mid-sized enterprise, medium SME, small SME and unclassified; the SME aggregate contains only the latter two. A micro-enterprise, if officially established, is a subtype of small SME. Do not infer legal size from employee count, stock listing, a job board's title or group revenue. An official certificate must match the exact company, be current at the stated as-of date and include provenance/rights before publishing a legal size classification. An unclassified company must be visible in search, not silently assigned to SME.

## Artifact and identity contract

Add `community-app/public/data/company-benefits/domestic-directory-v1/manifest.json` and bounded listing shards. Bind the directory manifest to the **raw byte hash** of the unchanged base `manifest.json` and the two acquisition source hashes. Each listing contains a synthetic `KR-BIZ-<10 digits>` ID for a source business number **only when no unambiguous exact DART bridge identifies one of the existing 1,000 base CRNs**; the 174 overlapping businesses are represented by those existing CRNs. This namespace means business-registration identity, *not* a verified 13-digit corporation ID or an independently employment-verified employer. No name-only merging. Latest posting day wins; if same-day names disagree, quarantine that ID. If source region or employee-count observations conflict on the chosen day, omit that field instead of picking arbitrarily. Restrict and escape all public text; no raw job titles or phone/address fields. Preserve the posting day and data edition separately. Every accepted ID must be unique across all shards; reported counts must be derived from the actual records, including every quarantined/overlapping-ID count. Include finite maximum file and record counts, payload hashes and byte counts, safe paths, no credentials, and a fail-closed build verifier. A process may regenerate the artifacts only from both restricted pinned inputs; no placeholder data.

The old 2,000-entity approved/research manifest, category outcomes, compare and fit flows stay byte-identical. Never blend 35K business-ID rows into verified benefit counts. The 12 base employer IDs with specific research-only actions can show their action counts and link to their existing detail, but new business-ID directory entries default to `공개 복지 정보 미확인`, not `복지 없음`. Do not invent benefits for a job posting.

## Product shape

Add a prominent first tab `국내 기업 검색` at `/community/benefits/directory/` and a strong entry link from the existing Benefit Atlas overview; retain the old heatmap/bookmarks and company pages. Only the directory route fetches the additive shards, with bounded concurrency and payload validation; the old atlas still loads only its existing 2,000 companies and 128 research actions. Search by full/partial company name and display a bounded page (maximum 50 DOM rows) with benefit-first badges, source type, dated location/employee observations when unambiguous, and size filter `대기업/중견기업/중기업/소기업/분류 미확인` with the SME parent grouping. A size category with no validated exact-ID certificate returns zero records and an honest explanation, not an inferred label. Show source details collapsed after any real benefit action and place a dedicated label `조사 중—승인 혜택 아님`. Unresearched companies remain searchable in the directory, while the existing benefit heatmap can continue to default to companies with actual research actions.

Static pagination/filtering must be deterministic, URL-safe, SSR-independent and mobile-readable. Display separate totals: base KR legal identities, new nonoverlapping recruitment business identities, companies with concrete research actions, and approved benefits. Don't add all job-posting rows to an enterprise total or describe the union as a current national registry.
