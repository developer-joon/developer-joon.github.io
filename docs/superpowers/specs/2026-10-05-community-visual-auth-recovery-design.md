# Community Jekyll Visual Alignment and Authenticated Entry Recovery Design

## Goal

Make Community look like a native `www.breadlab.ai` section on desktop and mobile, add an original Community banner at the same dimensions as the Blog banner, and eliminate the generic `요청을 처리하지 못했습니다` state reported immediately after an authenticated visitor enters Community.

## Confirmed production observations

- The production homepage-to-Community link performs a full-document navigation.
- Anonymous production checks pass for the Community home, six tag filters, three sort modes, search, post detail, and write route.
- The generic request error does not reproduce anonymously.
- The user reports the error immediately after entering Community while already signed in. The authenticated path therefore requires separate reproduction and regression coverage.
- Jekyll pages use a large image-backed `hero hero--single` banner. Community starts directly with its action row and content, which creates a visible transition even though its color tokens and responsive width breakpoints are similar.
- The user selected an original network-themed Community banner and requested Blog-equivalent banner dimensions, header spacing, content spacing, and font sizes.

## Visual design

### Shared Jekyll shell contract

Community will keep React ownership but render the public shell using the same structural layout contract as the Jekyll header and footer:

- brand and menu order remain `Ria & Seoa PaPa`, `0 → 1`, `Blog`, `Community`, `Shop`, `About`;
- desktop header width, top margin, logo size, menu font size, menu spacing, and breakpoint behavior match the values generated by the Jekyll theme;
- mobile focus trap, Escape close, focus restoration, scroll lock, and accessible menu labels remain intact;
- Community remains the active menu item;
- account identity, login/logout, and write actions remain outside the global navigation.

Community-specific controls will not load Jekyll's global stylesheet directly. Loading it would couple form, editor, and discussion controls to broad theme selectors. Instead, shared shell values will be represented explicitly in the Community stylesheet and guarded by contract tests against the Jekyll source values.

### Original Community banner

Create an original static SVG asset under the site's image assets. It will use a restrained dark blue-gray network composition with connected points and lines, avoiding third-party imagery and licensing risk.

The banner will:

- use the same height, responsive padding, overlay treatment, content width, and breakpoint behavior as Blog's `hero hero--single`;
- show only the visible title `자유게시판`;
- use Jekyll's heading size, weight, line height, and color at each breakpoint;
- place decorative SVG content away from the title's readability zone;
- expose no decorative image to assistive technology;
- preserve text contrast when the background image fails to load.

The existing in-content `자유게시판` hero heading will be removed so the page has one H1. Search, tags, sorting, and posts begin below the banner with Jekyll-equivalent content spacing.

### Community body alignment

- Outer widths remain aligned with Jekyll's responsive wraps: 500px, 680px, 900px, and 1100px.
- Desktop vertical spacing between header, banner, action row, tools, list, and footer will follow the rhythm used by Blog rather than the current standalone-app rhythm.
- Community-only English editorial labels such as `PUBLIC DESK` will be removed where they create a second visual language.
- Functional controls remain visibly interactive and retain accessible labels and keyboard behavior.
- Post cards, search, tags, and sorting remain Community components; this change aligns composition and typography without imitating Blog article cards that depend on featured images.

## Authenticated-entry error recovery

The public listing must remain available even when the persisted authentication session is stale or malformed.

Implementation will first add an authenticated-entry regression test and capture the repository error classification. The fix will follow the observed failure mode rather than weakening all payload validation:

1. Initialize authentication before treating the first authenticated request as final.
2. Classify invalid or expired JWT responses as authentication-session failures instead of a generic unknown error.
3. Clear only the unusable auth session through the Supabase auth client.
4. Retry the public read once as an anonymous read so Community remains readable.
5. Show a bounded notice asking the visitor to sign in again; do not show the generic full-page failure when the anonymous retry succeeds.
6. Do not retry mutations anonymously. Post creation, reactions, comments, reports, and moderation remain authenticated and fail closed.
7. Preserve strict response validation. Anonymous fallback must not accept malformed payloads.

If reproduction proves that the authenticated response payload, rather than the token, violates the contract, the server response will be corrected with a forward migration and tested for both anonymous and authenticated callers. The client validator will not be loosened to hide a server regression.

## Verification

### Automated

- Header structure, menu order, active state, desktop spacing, font sizes, and breakpoints.
- Banner asset existence, local origin, dimensions contract, overlay, heading typography, and one-H1 semantics.
- Community body widths and desktop/mobile spacing.
- Mobile menu keyboard lifecycle.
- Authenticated entry with a valid session.
- Expired/invalid persisted session recovery and one anonymous public-read retry.
- No anonymous retry for mutations.
- Existing repository payload validation, auth, draft, post, comment, and moderation tests.
- Typecheck, lint, build, static-site artifact verification, and DB tests if a migration is required.

### Production

- Enter Community from the production homepage on desktop and mobile.
- Confirm header geometry, font sizes, menu spacing, Blog-sized banner, and body alignment.
- Confirm anonymous home, all active tag filters, sort modes, search, and post detail.
- Confirm authenticated entry no longer displays `요청을 처리하지 못했습니다`.
- Confirm login identity and logout remain outside the global menu.
- Confirm post creation redirects to a working detail page.
- Verify the deployed GitHub Pages SHA and production Supabase migration state when applicable.

## Non-goals

- Activating GitHub or Kakao login.
- Replacing Community post cards with Blog article cards.
- Loading the entire Jekyll stylesheet into the React application.
- Relaxing UUID or payload validation.
- Changing Community data models or moderation behavior beyond the authenticated-entry defect.

## Acceptance criteria

1. Community has an original network-themed banner with the same responsive dimensions and title typography as Blog.
2. Community contains one visible H1, `자유게시판`.
3. PC header width, top spacing, brand size, menu font size, and menu gaps match other Jekyll pages.
4. Community body width and major vertical spacing no longer jump when navigating from another menu.
5. Mobile menu accessibility behavior remains intact.
6. A valid signed-in visitor can enter Community without a generic request error.
7. An invalid persisted session cannot prevent public Community content from loading and receives an actionable re-login notice.
8. Mutations never fall back to anonymous execution.
9. Anonymous and authenticated production paths are both verified before completion is reported.
